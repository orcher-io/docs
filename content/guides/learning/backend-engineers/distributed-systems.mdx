Before we explore more patterns, let's understand the fundamental distributed systems challenges that Orcher addresses. This knowledge will help you make better architectural decisions.

## The CAP Theorem and Orcher's Trade-offs

**CAP Theorem states that a distributed system can provide at most two of:**

- **Consistency (C)**: All nodes see the same data at the same time
- **Availability (A)**: Every request receives a response (success or failure)
- **Partition Tolerance (P)**: System continues operating despite network failures

**Orcher's Position:**

Orcher is built on PostgreSQL, which is a CP system (Consistency + Partition tolerance). Here's what that means for you:

**What You Get:**
- ✓ Strong consistency: Workflow state is always correct
- ✓ ACID transactions: No lost or corrupted workflow data
- ✓ Reliable journaling: Every step is durably recorded
- ✓ Partition tolerance: Can handle network failures (with retries)

**What You Trade:**
- ✗ Not available during PostgreSQL outages
- ✗ Requires database connectivity for all operations
- ✗ Single database is a bottleneck (though horizontal scaling is possible)

**Why This Trade-off Makes Sense:**

For workflow orchestration, **correctness is more important than availability**. Consider:

- No charge is created (no money is lost)
- Workflow retries when database recovers
- Customer gets consistent experience

```rust
#[task]
async fn add_credits_atomic(user_id: String, amount: i64) -> Result<()> {
    let mut tx = db.begin().await?;

    // SELECT FOR UPDATE locks the row
    tx.query("SELECT * FROM users WHERE id = $1 FOR UPDATE", user_id).await?;
    tx.query("UPDATE users SET balance = balance + $1 WHERE id = $2", amount, user_id).await?;

    tx.commit().await?;
    Ok(())
}
```

## Saga Pattern vs. Two-Phase Commit (2PC)

Both handle distributed transactions, but with different trade-offs.

#### Two-Phase Commit (2PC)

**How it works:**

1. **Prepare Phase**: Coordinator asks all participants: "Can you commit?"
2. **Commit Phase**: If all say yes, coordinator tells everyone to commit

**Problems with 2PC:**

1. **Blocking**: If coordinator crashes during commit phase, participants are stuck waiting
2. **Single point of failure**: Coordinator is critical
3. **Network partitions**: Can cause indefinite blocking
4. **Performance**: Requires multiple round-trips
5. **Lock contention**: Resources locked during entire protocol

#### Saga Pattern (Orcher's Approach)

**How it works:**

1. Execute each step sequentially
2. If step fails, execute compensating transactions for completed steps

Orcher makes the saga the natural choice: the "completed steps" list and the compensations are just journaled tasks, so a crash mid-rollback resumes the rollback — the coordinator-crash problem that sinks 2PC simply doesn't exist.

```rust
#[workflow]
pub async fn order_saga(ctx: WorkflowContext, order: Order) -> Result<String> {
    let mut completed_steps = Vec::new();

    // Try each step, track what succeeded
    match ctx.execute_task(reserve_inventory, order.items.clone()).await {
        Ok(reservation) => {
            completed_steps.push(CompensationStep::ReleaseInventory(reservation.id));

            match ctx.execute_task(charge_payment, order.amount).await {
                Ok(payment) => {
                    completed_steps.push(CompensationStep::RefundPayment(payment.id));

                    // Success! No compensation needed
                    return Ok(order.id);
                }
                Err(e) => {
                    // Compensate in reverse order
                    for step in completed_steps.iter().rev() {
                        compensate(ctx, step).await?;
                    }
                    return Err(e);
                }
            }
        }
        Err(e) => return Err(e),
    }
}
```

```python
        raise
```

**Saga vs. 2PC Comparison:**

| Aspect | Two-Phase Commit | Saga Pattern |
|--------|-----------------|--------------|
| **Isolation** | Full (locks held) | None (eventual consistency) |
| **Availability** | Low (blocking) | High (non-blocking) |
| **Complexity** | Protocol complexity | Business logic complexity |
| **Scalability** | Poor (coordinator bottleneck) | Good (independent steps) |
| **Failure handling** | Automatic rollback | Manual compensation |
| **Network partitions** | Deadlocks possible | Continues executing |
| **Performance** | Slower (multiple round-trips) | Faster (single-direction flow) |

**When to use each:**

- **2PC**: Banking transfers between accounts (need atomicity)
- **Saga**: E-commerce orders, booking systems, workflow orchestration

**Why Orcher uses Sagas:**

1. **Better availability**: Don't block on coordinator
2. **Simpler infrastructure**: No distributed coordinator needed
3. **Flexibility**: Compensation logic tailored to business needs
4. **Observability**: Can see exactly where a saga is in its progression
5. **Failure recovery**: Can retry individual steps

## Event Sourcing and Orcher's Journal

Orcher's workflow journal is similar to event sourcing, but optimized for workflows.

#### What is Event Sourcing?

Store all changes as a sequence of events instead of current state:

```rust
// Traditional (current state)
struct Account {
    id: String,
    balance: i64,  // Current balance only
}

// Event sourcing (full history)
enum AccountEvent {
    Created { id: String },
    Deposited { amount: i64 },
    Withdrawn { amount: i64 },
}

// Rebuild state by replaying events
let events = vec![
    AccountEvent::Created { id: "acc_123" },
    AccountEvent::Deposited { amount: 1000 },
    AccountEvent::Withdrawn { amount: 200 },
];

let balance = events.iter().fold(0, |bal, event| {
    match event {
        AccountEvent::Deposited { amount } => bal + amount,
        AccountEvent::Withdrawn { amount } => bal - amount,
        _ => bal,
    }
}); // balance = 800
```

#### Orcher's Journal as Event Store

The workflow journal is an event store for workflow execution:

```sql
-- Each journal entry is an event
SELECT * FROM workflow_execution_journal WHERE workflow_id = 'wf_123' ORDER BY step_id;

| step_id | task_name       | result                | created_at  |
|---------|-----------------|----------------------|-------------|
| 1       | create_user     | {"id": "user_456"}   | 10:00:00   |
| 2       | send_email      | {"sent": true}       | 10:00:01   |
| 3       | create_order    | {"id": "order_789"}  | 10:00:02   |
```

**Rebuilding workflow state:**

When a workflow resumes after a crash, the **worker re-runs your workflow function from the top**. Replay is not a server-side loop over journal rows — instead, the orchestrator hands the journal to the worker, and each task call consults it: any step that already completed returns its recorded result without executing again.

```rust
// The worker re-executes your workflow function. Each task call
// checks the journal before running:
async fn process_order(ctx: WorkflowContext, order: Order) -> Result<Receipt> {
    // Already in the journal → returns {"id": "user_123"}, does NOT run again
    let user = ctx.execute_task(create_user, order.clone()).await?;

    // Already in the journal → returns the cached result, email not re-sent
    ctx.execute_task(send_email, user.id.clone()).await?;

    // NOT in the journal → executes for the first time and is recorded
    let receipt = ctx.execute_task(create_order, user.id).await?;
    Ok(receipt)
}
```

#### Benefits of Orcher's Approach

**1. Time Travel Debugging**

See exactly what happened at any point:

```sql
-- What did the workflow do before crashing?
SELECT task_name, result, completed_at
FROM workflow_execution_journal
WHERE workflow_id = 'wf_failed_123'
ORDER BY step_id;
```

**2. Audit Trail**

Perfect record of all operations:

```sql
-- Did we charge this customer?
SELECT * FROM workflow_execution_journal
WHERE workflow_id = 'wf_payment_456'
  AND task_name = 'charge_stripe';
```

**3. Deterministic Replay**

Because the journal is an ordered, immutable record of what happened, re-running the workflow function against it always reproduces the same decisions in the same order. Replay happens automatically when a worker recovers an execution — there is no separate "replay this workflow" call. To exercise replay determinism in tests, use the [test environment](/guides/core/tasks/testing) to run a workflow and assert on its outcome.

**4. Performance Analysis**

Find bottlenecks:

```sql
SELECT
    task_name,
    AVG(EXTRACT(EPOCH FROM (completed_at - created_at))) as avg_seconds
FROM workflow_execution_journal
GROUP BY task_name
ORDER BY avg_seconds DESC;
```

```rust
#[task]
async fn update_and_read(user_id: String, amount: i64) -> Result<i64> {
    let mut tx = db.begin().await?;

    // Write to primary
    tx.query("UPDATE users SET balance = balance + $1 WHERE id = $2", amount, user_id).await?;

    // Read from same transaction (sees own write)
    let balance: i64 = tx.query_one(
        "SELECT balance FROM users WHERE id = $1",
        user_id
    ).await?.get(0);

    tx.commit().await?;
    Ok(balance)
}
```

```typescript
        const result = await client.query('SELECT balance FROM users WHERE id = $1', [input.userId]);
```

**Pattern 2: Conflict-Free Replicated Data Types (CRDTs)**

```rust
// ✓ Commutative updates
```

## The Write-Ahead Log (WAL) Pattern

Orcher's journal implements the WAL pattern used in databases.

**How WAL Works:**

1. **Before** executing operation, write intent to log
2. **Execute** the operation
3. **Mark** log entry as completed

**Why It's Reliable:**

```rust
// Step 1: Write to journal (durable)
journal.append(Entry {
    step_id: 5,
    task_name: "charge_stripe",
    input: payment_data,
    status: "pending",
}).await?;

// Step 2: Execute task
let result = charge_stripe_api(payment_data).await?;

// Step 3: Update journal (durable)
journal.update(5, JournalUpdate {
    result: result,
    status: "completed",
}).await?;

// If crash happens between step 2 and 3:
// - Journal shows "pending"
// - On restart, can retry or check if it actually succeeded
// - Never lose track of what was attempted
```

**Compare to non-WAL approach:**

```rust
// ❌ Without WAL
let result = charge_stripe_api(payment_data).await?; // ← CRASH HERE = lost money
db.save_payment(result).await?;
```

If crash happens after charging but before saving, the payment is lost forever.

**With Orcher's WAL:**

```rust
// ✓ With WAL
journal.append("charge_stripe", payment_data).await?; // ← Intent recorded
let result = charge_stripe_api(payment_data).await?;  // ← CRASH HERE = can recover
journal.complete("charge_stripe", result).await?;
```

Journal shows we attempted to charge. On recovery, check Stripe API to see if charge succeeded, then continue.

```rust
        return Err(WorkflowError::BusinessRule("High fraud risk".to_string()).into());
    }

    // Charge payment (may be transient failure)
    let charge = match ctx.execute_task(charge_stripe, payment.clone()).await {
        Ok(charge) => charge,
        Err(e) if is_transient_error(&e) => {
            warn!("Transient payment error: {}", e);
            return Err(WorkflowError::Transient(e.to_string()).into());
        }
        Err(e) => {
            return Err(WorkflowError::Permanent(format!("Payment failed: {}", e)).into());
        }
    };

    ctx.execute_task(save_payment, charge.id.clone())
        .await
        .context("Failed to save payment")?;

    Ok(Receipt {
        charge_id: charge.id,
        amount: payment.amount,
    })
}

fn is_transient_error(error: &anyhow::Error) -> bool {
    let error_str = error.to_string().to_lowercase();
    error_str.contains("timeout") ||
    error_str.contains("connection") ||
    error_str.contains("503") ||
    error_str.contains("rate limit")
}
```

#### Circuit Breaker Pattern

Protect external services from being overwhelmed during outages:

```rust
use std::sync::Arc;
use tokio::sync::RwLock;

pub struct CircuitBreaker {
    failure_threshold: u32,
    success_threshold: u32,
    timeout: Duration,
    state: Arc<RwLock<CircuitState>>,
}

enum CircuitState {
    Closed { failures: u32 },
    Open { opened_at: Instant },
    HalfOpen { successes: u32 },
}

impl CircuitBreaker {
    pub async fn call<F, T>(&self, f: F) -> Result<T>
    where
        F: FnOnce() -> Result<T>,
    {
        let mut state = self.state.write().await;

        match *state {
            CircuitState::Open { opened_at } => {
                // Check if timeout elapsed
                if opened_at.elapsed() > self.timeout {
                    *state = CircuitState::HalfOpen { successes: 0 };
                } else {
                    return Err(anyhow::anyhow!("Circuit breaker is OPEN"));
                }
            }
            _ => {}
        }

        drop(state); // Release lock before calling function

        let result = f();

        let mut state = self.state.write().await;
        match result {
            Ok(value) => {
                match *state {
                    CircuitState::HalfOpen { successes } => {
                        if successes + 1 >= self.success_threshold {
                            *state = CircuitState::Closed { failures: 0 };
                        } else {
                            *state = CircuitState::HalfOpen { successes: successes + 1 };
                        }
                    }
                    CircuitState::Closed { .. } => {
                        *state = CircuitState::Closed { failures: 0 };
                    }
                    _ => {}
                }
                Ok(value)
            }
            Err(e) => {
                match *state {
                    CircuitState::Closed { failures } => {
                        if failures + 1 >= self.failure_threshold {
                            *state = CircuitState::Open { opened_at: Instant::now() };
                        } else {
                            *state = CircuitState::Closed { failures: failures + 1 };
                        }
                    }
                    CircuitState::HalfOpen { .. } => {
                        *state = CircuitState::Open { opened_at: Instant::now() };
                    }
                    _ => {}
                }
                Err(e)
            }
        }
    }
}

// Use in task
#[task]
async fn call_external_service(data: String) -> Result<String> {
    static CIRCUIT_BREAKER: Lazy<CircuitBreaker> = Lazy::new(|| {
        CircuitBreaker::new(5, 2, Duration::from_secs(60))
    });

    CIRCUIT_BREAKER.call(|| {
        // Make actual API call
        external_api::process(data)
    }).await
}
```

## Pattern 7: Scheduled and Recurring Workflows

Orcher has no separate cron scheduler process. Instead, model recurrence as a long-running workflow that does its work, sleeps durably until the next run, then restarts with a fresh history. The durable workflow *is* the schedule — it survives restarts and frees the worker while it waits:
