## Understanding Durable Execution

Let's build a mental model of how durable execution works. This is the foundational concept that makes Orcher different from traditional backend architectures.

### What Is Durable Execution?

**Durable execution** means your code execution survives process crashes, network failures, and machine restarts. It's like having a built-in "save and resume" system for your business logic.

In traditional programming, when your process crashes, you lose:
- All in-memory state
- The exact position in your code
- Which operations completed vs. failed
- Any partial results

With durable execution, Orcher automatically preserves:
- **Execution position**: Which line of code was executing
- **Variable state**: Values of all task results
- **Decision history**: Which branches (if/else) were taken
- **Retry state**: How many attempts have been made

This is achieved through **automatic journaling** - every significant operation is recorded to durable storage (PostgreSQL) before, during, and after execution.

### The Problem: Partial Failures

Traditional code executes top-to-bottom. When it crashes, you lose everything:

```typescript
async function processOrder(order) {
  const charge = await stripe.charges.create({ amount: order.total }); // ← Succeeds
  await db.orders.update({ status: 'paid' });                          // ← Succeeds
  await emailService.send({ template: 'receipt' });                    // ← CRASHES
  await inventory.reserve(order.items);                                 // ← Never runs
  await analytics.track('order_completed');                             // ← Never runs
}
```

**What happened?**
- Customer was charged ✓
- Database updated ✓
- Email failed ✗
- Inventory not reserved ✗
- Analytics not tracked ✗

**What do you do?**
- Manually check Stripe for the charge
- Manually reserve inventory
- Manually send the email
- Manually track analytics
- Hope you didn't miss anything

This is called a **partial failure**, and it's the source of countless production incidents.

### The Solution: Automatic Journaling

Orcher wraps each step in a `ctx.execute_task()` call. This does three things:

1. **Before execution**: Checks if this step was already completed
2. **During execution**: Runs your code
3. **After execution**: Saves the result to the journal

Here's what the journal looks like in PostgreSQL:

```sql
SELECT * FROM workflow_execution_journal WHERE workflow_id = 'wf_abc123';

| step_id | task_name      | status    | result                    | created_at |
|---------|----------------|-----------|---------------------------|------------|
| 1       | charge_card    | completed | {"id": "ch_xyz", ...}     | 10:00:00   |
| 2       | update_db      | completed | null                      | 10:00:01   |
| 3       | send_email     | failed    | "SMTP timeout"            | 10:00:02   |
```

**On retry**, Orcher reads the journal:
- Step 1: Already completed → Return cached result
- Step 2: Already completed → Return cached result
- Step 3: Failed → Try again
- Step 4+: Not in journal → Execute normally

This is called **deterministic replay**.

### Execution Guarantees

Orcher provides three execution guarantees:

**1. A Completed Task Never Runs Again on Replay**

Once a task's result is journaled, replay reuses that result instead of running the task again. A task that has not recorded its result yet can run again, if its worker dies or it times out, so make its side effects idempotent.

**3. Crash Recovery with Progress Preservation**

If your workflow crashes at step 5 of 10, the retry starts at step 5. Steps 1-4 return their cached results instantly.

**Why These Guarantees Matter**

Traditional distributed systems achieve these guarantees through complex infrastructure:
- Two-phase commit protocols
- Distributed transaction coordinators
- Consensus algorithms (Paxos, Raft)
- Complex state machines

Orcher achieves them through a simple journal in PostgreSQL. The complexity is hidden in the runtime, not your code.

### Key Principle: Idempotency

Because Orcher may replay your workflow, each task must be **idempotent**: running it twice produces the same result.

**What is Idempotency?**

An operation is idempotent if executing it multiple times has the same effect as executing it once. Think of it like pressing an elevator button - pressing it 10 times doesn't call 10 elevators.

**Why Idempotency Matters in Orcher**

Even though Orcher never repeats a completed step *within a workflow*, your tasks might be called more than once in other scenarios:
- Workflow replays during development/testing
- Manual workflow retries from the admin UI
- Race conditions during deployments
- External retries (e.g., user clicking "submit" twice)

Making your tasks idempotent provides defense in depth.

**Good (idempotent):**

### Deep Dive: The Journal Structure

Let's look at what Orcher actually stores in PostgreSQL. Understanding this helps you reason about performance and debugging.

**Journal Table Schema:**

```sql
CREATE TABLE workflow_execution_journal (
    id UUID PRIMARY KEY,
    workflow_id UUID NOT NULL,
    step_id INTEGER NOT NULL,
    task_name TEXT NOT NULL,
    input JSONB NOT NULL,
    result JSONB,
    error TEXT,
    status TEXT NOT NULL, -- 'pending', 'completed', 'failed'
    attempt INTEGER NOT NULL DEFAULT 1,
    created_at TIMESTAMPTZ NOT NULL,
    completed_at TIMESTAMPTZ,

    UNIQUE(workflow_id, step_id)
);
```

**Example Journal Entries:**

```sql
-- Workflow: process_payment (wf_abc123)
SELECT step_id, task_name, status, result FROM workflow_execution_journal
WHERE workflow_id = 'wf_abc123'
ORDER BY step_id;

| step_id | task_name       | status    | result                                    |
|---------|-----------------|-----------|-------------------------------------------|
| 1       | validate_input  | completed | {"valid": true}                           |
| 2       | check_fraud     | completed | {"score": 0.12, "risk": "low"}            |
| 3       | charge_stripe   | completed | {"id": "ch_xyz", "amount": 5000, ...}     |
| 4       | save_to_db      | completed | {"payment_id": "pay_123"}                 |
| 5       | send_email      | failed    | null (error: "SMTP timeout")              |
```

**How Orcher Uses the Journal:**

1. **Before task execution**: Check if `(workflow_id, step_id)` exists
2. **If exists and completed**: Return `result` column (no execution)
3. **If not exists**: Execute task and INSERT new row
4. **If exists and failed**: Re-execute task and UPDATE row

**Performance Implications:**

- Each task execution = 1 SELECT + 1 INSERT/UPDATE query
- Journal queries use a unique index (very fast)
- Cached results return in ~1ms
- Trade-off: Durability for slight overhead

**Debugging with the Journal:**

```sql
-- Find all failed workflows
SELECT workflow_id, task_name, error
FROM workflow_execution_journal
WHERE status = 'failed';

-- See what a workflow did before crashing
SELECT task_name, result, completed_at
FROM workflow_execution_journal
WHERE workflow_id = 'wf_abc123'
ORDER BY step_id;

-- Find slow tasks
SELECT task_name, AVG(EXTRACT(EPOCH FROM (completed_at - created_at))) as avg_seconds
FROM workflow_execution_journal
WHERE status = 'completed'
GROUP BY task_name
ORDER BY avg_seconds DESC;
```

**What `ctx.execute_task()` does:**

1. **Generates a deterministic task ID** from the task name and workflow position
2. **Checks the journal** for an existing result
3. **If found**: Returns the cached result instantly (no execution)
4. **If not found**: Executes the task and journals the result
5. **On failure**: Throws an error (workflow can be retried)

**Important**: Task results must be serializable (JSON). Orcher stores them in PostgreSQL.

## Workflows vs Tasks

Understanding the difference is crucial:

**Workflow** = The orchestration logic
- Defines the sequence of steps
- Makes decisions (if/else, loops)
- Handles errors and retries
- Coordinates multiple tasks
- Can call other workflows (child workflows)

**Task** = A single unit of work
- Performs one specific action
- Should be idempotent
- Returns a serializable result
- Can be retried independently

## Consistency Models Explained

Understanding Orcher's consistency guarantees helps you build correct distributed systems.

### Workflow Isolation

Each workflow execution is isolated - they don't see each other's uncommitted state.

```rust
#[task]
async fn add_credits_safely(user_id: String, amount: i64) -> Result<()> {
    let mut tx = db.begin().await?;

    // SELECT FOR UPDATE locks the row
    tx.query("SELECT balance FROM users WHERE id = $1 FOR UPDATE", user_id).await?;
    tx.query("UPDATE users SET balance = balance + $1 WHERE id = $2", amount, user_id).await?;

    tx.commit().await?;
    Ok(())
}
```

```typescript
@Task()
async addCreditsSafely(ctx: TaskContext, input: { userId: string; amount: number }): Promise<void> {
    const client = await pool.connect();
    try {
        await client.query('BEGIN');
        // SELECT FOR UPDATE locks the row
        await client.query('SELECT balance FROM users WHERE id = $1 FOR UPDATE', [input.userId]);
        await client.query('UPDATE users SET balance = balance + $1 WHERE id = $2', [input.amount, input.userId]);
        await client.query('COMMIT');
    } catch (e) {
        await client.query('ROLLBACK');
        throw e;
    } finally {
```

### Once per Step, at Least Once per Task

A workflow never re-runs a step whose result is journaled, but a task itself runs **at least once**: if its worker dies before reporting, or a timeout fires, it runs again, so its side effects must be idempotent.

**What does this mean?**

## Architecture Deep Dive

Let's understand how Orcher fits into your system and the engineering decisions behind its design.

### Component Overview

Orcher uses a **client-server architecture**: an Orchestrator server handles workflow state, journaling, and queue management, while SDK Workers connect to it via gRPC to execute your workflow and task code. The architecture has three layers:

**Layer 1 — Orchestrator Server**

- **gRPC API** (port 50051): Accepts workflow start requests, polls from workers, and delivers task assignments
- **HTTP API** (port 8001): Provides management endpoints, health checks, and observability
- **Workflow Engine**: Manages workflow state, journaling, deterministic replay, retry policies, and queue dispatch

The Orchestrator server is a standalone process that you deploy alongside your application infrastructure.

**Layer 2 — SDK Workers (your application process)**

- **Worker**: Connects to the Orchestrator server via gRPC and registers your workflows and tasks
- **Worker Pool**: Long-polls the Orchestrator for pending workflows and tasks, then executes them locally
- **API Server** (optional): Your HTTP server can use the Orcher client SDK to start workflows by calling the Orchestrator's gRPC API

Workers run your business logic. They do not store workflow state themselves -- all state lives in the Orchestrator's database.

**Layer 3 — PostgreSQL**

- Workflow journal (execution history)
- Queue table (pending workflows)
- Task execution tracking
- Managed entirely by the Orchestrator server

**Key Points:**

1. **Client-Server Model**: The Orchestrator server is a separate process; SDK Workers connect to it over the network
2. **Single Database**: The Orchestrator stores everything in PostgreSQL (simpler operations)
3. **Worker Pattern**: Your application runs as one or more SDK Workers that long-poll the Orchestrator for work
4. **No Message Queue**: PostgreSQL acts as the queue (SKIP LOCKED queries), managed by the Orchestrator

## Retry Policies and Error Handling

Orcher provides sophisticated retry mechanisms out of the box.

### Default Retry Behavior

When a task fails, Orcher automatically retries with exponential backoff:

```text
Attempt 1: Immediate
Attempt 2: 1 second later
Attempt 3: 2 seconds later
Attempt 4: 4 seconds later
Attempt 5: 8 seconds later
Attempt 6: 16 seconds later
...
Max: 24 hours between retries
```

**Why exponential backoff?**
- Transient errors (network blip) resolve quickly → fast retry
- Service outages need time to recover → don't overwhelm
- Cascading failures prevented by increasing delays

```typescript
        try {
            charge = await ctx.executeTask(tasks.chargeCard, booking.payment);
        } catch (e) {
            // Payment failed - compensate by releasing seat
            await ctx.executeTask(tasks.releaseSeat, reservation.id);
            throw e;
        }

        // Step 3: Send confirmation
        await ctx.executeTask(tasks.sendConfirmation, charge.receipt);

        return { bookingId: charge.id };
    }
}
```

```python
@workflow(name="book_flight", version="1.0.0")
async def book_flight(ctx: WorkflowContext, booking: dict) -> dict:
    # Step 1: Reserve seat
    reservation = await ctx.execute_task(reserve_seat, seat_id=booking["seat_id"])

    # Step 2: Charge payment
    try:
        charge = await ctx.execute_task(charge_card, payment=booking["payment"])
    except Exception as e:
        # Payment failed - compensate by releasing seat
        await ctx.execute_task(release_seat, reservation_id=reservation["id"])
        raise

    # Step 3: Send confirmation
    await ctx.execute_task(send_confirmation, receipt=charge["receipt"])

    return {"booking_id": charge["id"]}
```
