You already know the shape of an ETL job: pull data from a source, clean it, write it to a destination. And you know the part that actually hurts — **what happens when it dies at row 847,392 of a million?** Everything in this section is about that question, so let's start there.

## The problem you're used to solving

Restartable pipelines are a solved problem, and you've solved it before. The catch is *how much machinery* it took:

- **Re-run the whole job.** Simple, and fine at small scale — but re-reading a million rows and re-hitting every API to recover from a failure at 90% is expensive and slow.
- **A manual state table.** You track `last_processed_offset` in Postgres yourself, read it on startup, update it as you go. Now you own a second source of truth that can drift from the actual work.
- **Scheduler or Spark checkpoints.** A scheduler that passes intermediate results between steps, or Spark's checkpoint directories. Real checkpointing — but it's infrastructure you run, tune, and debug.

All three are answers to one question: *where did I get to, and how do I not redo it?* Orcher's answer is that you don't implement the answer at all — the runtime already knows, because it journals every step.

## Your First ETL Pipeline

We'll build a pipeline that imports a CSV of customers into a database, in batches, with crash recovery — piece by piece. Each piece is a **task**: a unit of work Orcher journals when it completes. Read it in whichever language you'll use; the tabs stay in sync as you go, and the [complete file](#the-complete-pipeline) is at the end to copy.

### Step 1 — Count the work

First, how many rows are we importing? Counting is its own task, so the total lands in the journal once. On a restart, the pipeline doesn't re-read the file to recount — it reads the number back from where it left off.

### Step 2 — Extract and transform one batch

Now the per-batch work. `extract_batch` pulls a slice using offset/limit pagination — a familiar cursor over the source — and `transform_batch` cleans it: drop rows without a valid email, normalize the rest. Keep transforms **pure** (same input → same output): a deterministic transform replays safely, a random or clock-dependent one does not.

### Step 3 — Load without duplicates

This is the step that makes durability *safe*. A task can be retried after a failure — so if `load_batch` writes rows and then the worker dies before the result is journaled, the retry runs the write **again**. A plain `INSERT` would double-load that batch. An **UPSERT** (`INSERT ... ON CONFLICT DO UPDATE`) makes re-running the same batch a no-op: the rows already there are updated in place, not duplicated. This is the single most important habit in durable data work — writes must be idempotent.

<Tabs scrollable size="small" type="underlined" defaultActiveId="typescript" queryGroup="language">
<TabPanel id="typescript" label="TypeScript">

```typescript
@Task()
async loadBatch(ctx: TaskContext, rows: CleanedRow[]): Promise<number> {
  // UPSERT ensures idempotency on retry
  const result = await db.query(`
    INSERT INTO customers (email, name, amount, created_at)
    SELECT * FROM UNNEST($1::text[], $2::text[], $3::numeric[], $4::timestamptz[])
    ON CONFLICT (email) DO UPDATE SET
      name = EXCLUDED.name,
      amount = EXCLUDED.amount,
      created_at = EXCLUDED.created_at
  `, [rows.map(r => r.email), rows.map(r => r.name), rows.map(r => r.amount), rows.map(r => r.createdAt)]);
  return result.rowCount;
}
```

### Step 4 — Orchestrate the batches

The workflow ties the tasks together: count once, then loop over batches running extract → transform → load. Every `execute_task` call is a journaled checkpoint, so the loop index is effectively durable state — there's no offset table because the journal *is* the offset. Crash at batch 500 of 1,000, and recovery replays the 499 finished batches instantly and resumes at 500.

<Tabs scrollable size="small" type="underlined" defaultActiveId="typescript" queryGroup="language">
<TabPanel id="typescript" label="TypeScript">

```typescript
@Workflow({ name: 'csv_import', version: '1.0.0' })
class CsvImport {
  async run(ctx: WorkflowContext, input: CsvImportInput): Promise<number> {
    const totalRows = await ctx.executeTask(tasks.countRows, input.filePath);
    const numBatches = Math.ceil(totalRows / input.batchSize);
    let totalLoaded = 0;

    for (let i = 0; i < numBatches; i++) {
      // Each of these 3 steps is journaled — crash recovery resumes here
      const rows = await ctx.executeTask(tasks.extractBatch, {
        filePath: input.filePath,
        offset: i * input.batchSize,
        limit: input.batchSize,
      });
      const cleaned = await ctx.executeTask(tasks.transformBatch, rows);
      const loaded = await ctx.executeTask(tasks.loadBatch, cleaned);
      totalLoaded += loaded;
    }

    return totalLoaded;
  }
}
```

**Key principle**: every `execute_task` call is journaled. On crash recovery, completed steps return cached results instantly — no re-execution, no duplicate API calls, no duplicate database inserts. You wrote the pipeline; Orcher supplied the durability.

### The complete pipeline

Here's everything above assembled into one file.

```typescript
import {
  Workflow,
  Tasks,
  Task,
  TaskContext,
  WorkflowContext,
  createTaskRefs,
} from '@orcher/sdk';

interface CsvImportInput {
  filePath: string;
  batchSize: number;
}

@Tasks()
class EtlTasks {
  @Task()
  async countRows(ctx: TaskContext, filePath: string): Promise<number> {
    const content = await fs.readFile(filePath, 'utf-8');
    return content.split('\n').length - 1; // exclude header
  }

  @Task()
  async extractBatch(ctx: TaskContext, input: { filePath: string; offset: number; limit: number }): Promise<Record<string, string>[]> {
    return await csvParser.readBatch(input.filePath, input.offset, input.limit);
  }

  @Task()
  async transformBatch(ctx: TaskContext, rows: Record<string, string>[]): Promise<CleanedRow[]> {
    return rows
      .filter(row => row.email && row.email.includes('@'))
      .map(row => ({
        email: row.email.toLowerCase().trim(),
        name: row.name?.trim() ?? '',
        amount: parseFloat(row.amount) || 0,
        createdAt: new Date(row.created_at).toISOString(),
      }));
  }

  @Task()
  async loadBatch(ctx: TaskContext, rows: CleanedRow[]): Promise<number> {
    // UPSERT ensures idempotency on retry
    const result = await db.query(`
      INSERT INTO customers (email, name, amount, created_at)
      SELECT * FROM UNNEST($1::text[], $2::text[], $3::numeric[], $4::timestamptz[])
      ON CONFLICT (email) DO UPDATE SET
        name = EXCLUDED.name,
        amount = EXCLUDED.amount,
        created_at = EXCLUDED.created_at
    `, [rows.map(r => r.email), rows.map(r => r.name), rows.map(r => r.amount), rows.map(r => r.createdAt)]);
    return result.rowCount;
  }
}

const tasks = createTaskRefs(EtlTasks);

@Workflow({ name: 'csv_import', version: '1.0.0' })
class CsvImport {
  async run(ctx: WorkflowContext, input: CsvImportInput): Promise<number> {
    const totalRows = await ctx.executeTask(tasks.countRows, input.filePath);
    const numBatches = Math.ceil(totalRows / input.batchSize);
    let totalLoaded = 0;

    for (let i = 0; i < numBatches; i++) {
      const rows = await ctx.executeTask(tasks.extractBatch, {
        filePath: input.filePath,
        offset: i * input.batchSize,
        limit: input.batchSize,
      });
      const cleaned = await ctx.executeTask(tasks.transformBatch, rows);
      const loaded = await ctx.executeTask(tasks.loadBatch, cleaned);
      totalLoaded += loaded;
    }

    return totalLoaded;
  }
}

## Automatic Checkpointing

Traditional pipelines require manual checkpoint management. Orcher journals every task result automatically, so your checkpoint is always the last completed task. Picture a four-stage pipeline that crashes after validation — here's exactly what runs, and what doesn't, on recovery:

The mental shift is worth stating plainly, because it's the one that carries through the rest of this path:

| What you'd reach for | What Orcher does instead |
| --- | --- |
| Spark checkpoint directory, a scheduler's intermediate results, or a hand-rolled `job_state` table | Every `execute_task` result is journaled automatically |
| Read state on startup, decide where to resume | Replay returns completed steps from the journal; execution continues at the first unfinished one |
| Dedup or "already processed?" guards so a retry doesn't double-write | Completed tasks are never re-executed — the guard is the journal |

You still design the *pipeline*; Orcher owns the *bookkeeping*. That trade — you keep the logic, the runtime keeps the durability — is the through-line of everything below.

@Workflow({ name: 'multi_stage_pipeline', version: '1.0.0' })
class MultiStagePipeline {
  async run(ctx: WorkflowContext, source: string): Promise<PipelineResult> {
    // Step 1: Extract (journaled)
    const raw = await ctx.executeTask(tasks.extract, source);

    // Step 2: Validate (journaled)
    const valid = await ctx.executeTask(tasks.validate, raw);

    // Step 3: Enrich (journaled)
    const enriched = await ctx.executeTask(tasks.enrich, valid);

    // Step 4: Load (journaled)
    const result = await ctx.executeTask(tasks.load, enriched);

    // If crash happens after step 2 but before step 3:
    // → Steps 1-2 return cached results instantly (no re-execution)
    // → Step 3 executes fresh and continues from there

    return result;
  }
}
```
