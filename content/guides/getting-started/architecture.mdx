Orcher has three parts. The engine coordinates runs and keeps no state of its own. Your workers are your own processes, running your workflows and tasks on an Orcher SDK. PostgreSQL holds every run, journal entry, task and timer, and is the only thing the engine depends on.

## System Overview

<ArchitectureDiagram />

- **Engine** — Serves the gRPC API on port `50051`, and the REST API, the dashboard, health checks and metrics on port `8080`. It dispatches runs and tasks to workers, records results in the journal, fires timers and starts scheduled runs.
- **Workers** — Your processes. They call in to the engine and wait for work on a long poll; the engine never calls them. A worker runs your workflow code and your task code.
- **PostgreSQL** — Holds all state. Because nothing lives in the engine, it can be stopped, restarted or replaced at any time and every run carries on.

## Code-First Design

Unlike configuration-driven orchestrators that require YAML or DSL definitions, Orcher workflows are written as regular async functions decorated with macros (Rust) or decorators (TypeScript/Python). This means your workflows live in the same codebase as your application, benefit from compile-time type checking, and can be tested with standard unit testing frameworks.

    Ok(Payment { /* ... */ })

    // Create shipment
    Ok(Shipment { /* ... */ })
}

#[workflow]
async fn order_workflow(ctx: WorkflowContext, order: Order) -> Result<OrderResult> {
    let validated = ctx.execute_task(validate_order, order).await?;
    let payment = ctx.execute_task(process_payment, validated).await?;
    let shipped = ctx.execute_task(ship_order, payment).await?;
    Ok(OrderResult { shipped })
}

```typescript
import { Workflow, Tasks, Task, TaskContext, WorkflowContext, createTaskRefs } from '@orcher/sdk';

@Tasks()
class OrderTasks {
  @Task()
  async validateOrder(ctx: TaskContext, order: Order): Promise<ValidatedOrder> {
    // Validate the order
    return { /* ... */ };
  }

  @Task()
  async processPayment(ctx: TaskContext, order: ValidatedOrder): Promise<Payment> {
    // Charge the customer
    return { /* ... */ };
  }

  @Task()
  async shipOrder(ctx: TaskContext, payment: Payment): Promise<Shipment> {
    // Create shipment
    return { /* ... */ };
  }
}

const tasks = createTaskRefs(OrderTasks);

@Workflow({ name: 'order_workflow', version: '1.0.0' })
class OrderWorkflow {
  async run(ctx: WorkflowContext, order: Order): Promise<OrderResult> {
    const validated = await ctx.executeTask(tasks.validateOrder, order);
    const payment = await ctx.executeTask(tasks.processPayment, validated);
    const shipped = await ctx.executeTask(tasks.shipOrder, payment);
    return { shipped };
  }
}
```

from orcher import workflow, task, WorkflowContext, TaskContext

@task(name="validate_order")
async def validate_order(ctx: TaskContext, order: Order) -> ValidatedOrder:
    # Validate the order
    return ValidatedOrder(...)

async def process_payment(ctx: TaskContext, order: ValidatedOrder) -> Payment:
    # Charge the customer
    return Payment(...)

@task(name="ship_order")
async def ship_order(ctx: TaskContext, payment: Payment) -> Shipment:
    # Create shipment
    return Shipment(...)

@workflow(name="order_workflow", version="1.0.0")
async def order_workflow(ctx: WorkflowContext, order: Order) -> OrderResult:
    validated = await ctx.execute_task(validate_order, order=order)
    payment = await ctx.execute_task(process_payment, order=validated)
    shipped = await ctx.execute_task(ship_order, payment=payment)
    return OrderResult(shipped=shipped)

## Your Code Runs in Your Workers

Workflows and tasks run inside your own worker processes, not in a runtime Orcher provides. A worker is your application with an Orcher SDK added: it uses your libraries, your configuration and your access to your own services and databases. The engine never runs your code; it only decides what runs next and records what happened.

Workers talk to the engine over gRPC. Each task is handed to a worker by the engine and its result is reported back, so a step of a workflow is a round trip to the engine, not a function call.

## Automatic Journaling

You write no checkpointing code. When a task completes, its result and the journal entry that records it are committed to PostgreSQL in one transaction. When a workflow resumes, after a crash or simply after waiting, its code runs again from the top and each step that is already in the journal returns its recorded result instead of running again.

Tasks run at least once: a task whose worker died part way runs again. Only one result is recorded. [Guarantees](/guides/core/guarantees) sets out exactly what is promised.

## Typed Workflows and Tasks

In Rust, a workflow refers to its tasks through typed references, so calling a task that does not exist, or passing it the wrong input type, is a compile error. In TypeScript, task references created with `createTaskRefs` are typed in the same way. Python has no such check before the code runs.

## Eager Dispatch

When a task completes and the same workflow has its next task ready, the engine can hand that task back in its reply to the completion, saving the worker a separate poll for it.

```
Without:  complete task → poll → receive next task
Eager:    complete task → receive next task
```

The worker takes the task under a short claim. If it does not start the task within 10 seconds, the engine puts the task back for any worker to poll; a task with a heartbeat or a timeout of its own is recovered by that instead. Eager dispatch only saves a round trip; it never lets a task run that would not otherwise have run.

## Events

A workflow can wait for a named event with `wait_for_event`, and resume when one is sent to it. Events are kept in the journal, so an event is not lost if a worker stops, and an event sent before the workflow waits is kept until it does.

- **From outside** — Your application or a webhook handler sends an event through the gRPC API or a workflow handle in any SDK.
- **Between workflows** — A workflow sends an event to another through that workflow's handle.
- **With a deadline** — `wait_for_event_with_timeout` returns nothing if no event arrives in time, so the workflow can escalate or fall back.

## Scaling

Add workers to do more work at once. Each worker polls the task queues it serves and runs tasks independently, and a task queue spreads its work across every worker polling it. Use separate task queues to keep kinds of work apart, or to send work to workers with particular resources.

Run one engine. Because all state is in PostgreSQL, restarting or replacing the engine loses nothing, and runs carry on once it is back.
