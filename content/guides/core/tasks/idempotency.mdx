Tasks should be designed to be safely retried without causing duplicate side effects.

### Using Idempotency Keys

A task runs **at least once**. If a worker charges a card and then crashes before its result reaches the engine, the journal has no result for that step, so the engine retries the task once its start-to-close or heartbeat timeout expires, and the task calls the payment provider again. Replay cannot prevent this: it only skips steps whose results are already in the journal.

Pass the external system an idempotency key that is **the same on every attempt**, so a repeated call returns the original result instead of acting twice. Build it from a business id (an order or payment id), or from the workflow id together with the task id (Rust `ctx.workflow_id()` and `ctx.task_id()`, TypeScript `ctx.workflowId()` and `ctx.taskId()`, Python `ctx.info.workflow_id` and `ctx.task_id`). The task id stays the same across a task's retries, but it is numbered within one workflow, so the same id appears in every workflow: on its own, two customers' charges would share a key. Never include the attempt number: that gives each retry a new key, and the provider would charge again.

```rust
#[task(
name = "charge_card",
retry = 3  // ← Task may be retried up to 3 times
)]
pub async fn charge_card(
_ctx: TaskContext,
input: PaymentInput,
) -> Result<ChargeResult> {
// Get Stripe API client
let stripe_client = get_stripe_client();

// Create charge with idempotency key
let charge = stripe::Charge::create(
    &stripe_client,
    ChargeParams {
        amount: input.amount,        // e.g., 5000 (= $50.00)
        currency: "usd",              // USD currency
        source: input.card_token,     // Customer's card token

        // ⭐ THE KEY LINE: Idempotency key prevents duplicate charges
        // Format: "order_12345"
        // If Stripe sees this key again, it returns the original charge
        // without creating a new one
        idempotency_key: Some(format!("order_{}", input.order_id)),
        ..Default::default()
    }
).await?;

// Return charge details
Ok(ChargeResult {
    charge_id: charge.id,         // e.g., "ch_abc123"
    amount: charge.amount,         // 5000
    status: "succeeded".to_string(),
})
}
```

**What happens when the worker crashes after the charge:**

1. Attempt 1 sends the charge with key `order_12345`; Stripe charges the card.
2. The worker crashes before reporting the result, so the journal has none.
3. The task's timeout expires and the engine schedules attempt 2.
4. Attempt 2 sends the same key; Stripe returns the original charge and does not charge again.
5. The result reaches the journal. From then on, replay returns it without running the task.

**Key Takeaways:**
- A task can run more than once, so every external side effect needs a key the external system deduplicates on
- Base the key on something stable: an order id, a payment id, or the workflow id with the task id; never a timestamp, the attempt number, or the task id alone
- The journal covers steps whose results it recorded; the key covers the gap between the side effect and that record
- Set a start-to-close or heartbeat timeout so a task lost with its worker is retried promptly

### Generating the key in the workflow

When no business id exists yet, generate the key in the workflow and pass it to the task as input. A workflow's random values are deterministic, so the key is the same on every replay and on every retry of the task.

### Strategy 2: Database Upsert Pattern

**Concept:** Use database operations that are naturally idempotent (INSERT ON CONFLICT, UPSERT, atomic UPDATE).

**When to Use:**
- Database writes
- Inventory management
- Counter updates
- Status changes

**How It Works:**

Instead of read-modify-write (which is NOT idempotent), use atomic database operations that produce the same result when run multiple times.

**Complete Example with Breakdown:**

  type="underlined"

<TabPanel id="rust" label="Rust">

```rust
#[task(name = "update_inventory")]
pub async fn update_inventory(
_ctx: TaskContext,
input: InventoryUpdate,
) -> Result<()> {
let db = get_database();

// Use UPSERT (INSERT ... ON CONFLICT) for idempotency
db.execute(
    "INSERT INTO inventory (product_id, quantity, updated_at)
     VALUES ($1, $2, NOW())
     ON CONFLICT (product_id)
     DO UPDATE SET
       quantity = $2,
       updated_at = NOW()",
    &[&input.product_id, &input.quantity]
).await?;

Ok(())
}
```

### Check-Before-Execute Pattern

Before performing a non-idempotent operation, check whether it has already been done. This pattern is useful when the external system doesn't support idempotency keys — you query the current state first and skip the operation if it was already applied.

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="language"
>

<TabPanel id="rust" label="Rust">

```rust
#[task(name = "send_welcome_email")]
pub async fn send_welcome_email(
_ctx: TaskContext,
user_id: String,
) -> Result<EmailResult> {
let db = get_database();

// Check if email was already sent
let already_sent: bool = db.query_one(
    "SELECT EXISTS(
       SELECT 1 FROM sent_emails
       WHERE user_id = $1 AND email_type = 'welcome'
     )",
    &[&user_id]
).await?;

if already_sent {
    tracing::info!("Email already sent to user {}", user_id);
    return Ok(EmailResult {
        message_id: "already_sent".to_string(),
        sent: false,
    });
}

// Send email
let result = email_service::send_welcome(&user_id).await?;

// Record that email was sent
db.execute(
    "INSERT INTO sent_emails (user_id, email_type, message_id)
     VALUES ($1, 'welcome', $2)",
    &[&user_id, &result.message_id]
).await?;

Ok(result)
}
```

### Error Handling

Tasks should handle errors appropriately and return meaningful error messages.

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="language"
>

<TabPanel id="rust" label="Rust">

```rust
use anyhow::{Context, Result};

#[task(
name = "fetch_external_data",
retry = 5
)]
pub async fn fetch_external_data(
ctx: TaskContext,
url: String,
) -> Result<ApiResponse> {
let response = reqwest::get(&url)
    .await
    .context("Failed to connect to API")?;

match response.status() {
    status if status.is_success() => {
        let data = response.json().await?;
        Ok(data)
    }
    status if status.is_server_error() => {
        // 5xx errors are transient - should retry
        Err(anyhow::anyhow!(
            "Server error (will retry): HTTP {}",
            status
        ))
    }
    status => {
        // 4xx errors are permanent - don't retry
        Err(anyhow::anyhow!(
            "Client error (permanent): HTTP {}",
            status
        ))
    }
}
}
```

</TabPanel>

<TabPanel id="typescript" label="TypeScript">

```typescript
// Inside a @Tasks() class:
@Task({
  name: 'fetchExternalData',
  retryPolicy: {
    maxAttempts: 5,
    nonRetryableErrorTypes: ['ClientError'],
  },
})
async fetchExternalData(
  _ctx: TaskContext,
  url: string
): Promise<ApiResponse> {
  const response = await fetch(url);

  if (response.ok) {
return response.json();
  }

  if (response.status >= 500) {
// 5xx errors are transient - should retry
throw new Error(`Server error (will retry): HTTP ${response.status}`);
  }

  // 4xx errors are permanent - mark as non-retryable
  const error = new Error(`Client error: HTTP ${response.status}`);
  error.name = 'ClientError';
  throw error;
}
```

</TabPanel>

<TabPanel id="python" label="Python">

```python
import httpx
from orcher import task, TaskContext
from orcher.errors import ApplicationFailure

@task(
name="fetch_external_data",
retry_policy={"max_attempts": 5},
)
async def fetch_external_data(ctx: TaskContext, url: str) -> dict:
async with httpx.AsyncClient() as client:
    response = await client.get(url)

if response.is_success:
    return response.json()

if response.status_code >= 500:
    # 5xx errors are transient - should retry
    raise RuntimeError(
        f"Server error (will retry): HTTP {response.status_code}"
    )

# 4xx errors are permanent - mark as non-retryable
raise ApplicationFailure(
    message=f"Client error: HTTP {response.status_code}",
    error_type="ClientError",
    retryable=False,
)
```
