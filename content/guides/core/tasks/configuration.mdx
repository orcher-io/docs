Task macros and decorators accept configuration attributes that control naming, routing, retries, timeouts, and resource requirements. These are set at definition time and apply to every invocation of the task.

### Standalone vs Grouped Tasks

Orcher supports two patterns for defining tasks:

- **Standalone tasks** — individual functions decorated with `#[task]` (Rust), `@Task()` (TypeScript), or `@task` (Python)
- **Task groups** (Rust) — multiple `#[task]` methods on an impl block via `#[tasks]`, with group-level defaults

Both patterns produce the same runtime behavior. Task groups are purely an organizational and DX feature — they register tasks identically to standalone functions.

### Basic Attributes

Every task has a name and a task queue. The name identifies the task type for routing and observability. The task queue determines which workers receive the task.

### Retry Configuration

Configure how many times a task is retried on failure and the delay strategy between attempts. You can set a maximum number of attempts, initial and maximum backoff intervals, and a backoff coefficient for exponential delay growth.

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="language"
>

<TabPanel id="rust" label="Rust">

```rust
// Simple retry (exponential backoff)
#[task(
name = "fetch_data",
retry = 5  // Retry up to 5 times with exponential backoff
)]
pub async fn fetch_data(
_ctx: TaskContext,
url: String,
) -> Result<String> {
let response = reqwest::get(&url).await?.text().await?;
Ok(response)
}

// Advanced retry policy
#[task(
name = "flaky_operation",
retry_policy(
    max_attempts = 5,
    initial_interval = 1,        // Start with 1 second delay
    max_interval = 60,           // Cap at 60 seconds
    backoff_coefficient = 2.0    // Double delay each retry
)
)]
pub async fn flaky_operation(
ctx: TaskContext,
input: OperationInput,
) -> Result<OperationResult> {
// Will retry with delays: 1s, 2s, 4s, 8s, 16s
if ctx.is_retry() {
    tracing::warn!("Retrying operation (attempt {})", ctx.attempt());
}

// Implementation
Ok(result)
}
```

### Timeout Configuration

Two independent limits bound a task. The **queue limit** (`schedule_to_start`) caps how long it may wait to be picked up; the **run limit** (`start_to_close`) caps how long it may run once started. Exceeding either marks the task timed out, and it is retried according to its retry policy.

They are set separately because they answer different questions. A nightly reconciliation job may legitimately queue for an hour and must not run for more than ten minutes; a payment capture must start within seconds and may take a minute. Setting only a run limit leaves the wait unbounded, which is the right default — a task that has not started yet has not misbehaved.

### Per-Call Timeouts

Limits declared on the task apply to every invocation. When one call needs
different bounds — the same task used for an interactive request and for a
nightly backfill — set them where the task is scheduled. Call-site values take
precedence.

<Tabs
  scrollable

  type="underlined"
  defaultActiveId="rust"
  queryGroup="language"
>

<TabPanel id="rust" label="Rust">

```rust
use std::time::Duration;
use orcher::workflow::TaskOptions;

ctx.execute_task_with_options(
    "charge_card",
    input,
    TaskOptions {
        // How long it may run once a worker starts it.
        timeout: Some(Duration::from_secs(90)),
        // How long it may wait to be started. Omit for no queue limit.
        queue_timeout: Some(Duration::from_secs(10)),
        // Kill the task if it stops heartbeating for this long.
        heartbeat_timeout: Some(Duration::from_secs(30)),
        ..Default::default()
    },
).await?
```

<Admonition type="note">

`timeout` bounds only the run. Omitting `queue_timeout` leaves the wait unbounded rather than reusing the run limit, so a task given a 90s run limit is not also given 90s to start — the two never sum into a total you did not ask for.

</Admonition>

### Task Groups (Rust)

In the Rust SDK, you can group related tasks under a struct using the `#[tasks]` macro. This provides:

- **Shared defaults** — set retry, timeout, task queue, etc. once for all tasks in the group
- **Per-task overrides** — any method-level `#[task(...)]` attribute overrides the group default
- **Type-safe references** — `StructName::method` works as a `TaskReference` for `ctx.execute_task()`
- **Code organization** — logically group related tasks, add helper methods

```rust
use orcher::prelude::*;

pub struct NotificationTasks;

#[tasks(retry = 3, timeout = 30, namespace = "notifications")]
impl NotificationTasks {
    #[task]
    async fn send_email(ctx: TaskContext, input: EmailInput) -> Result<EmailResult> {
        // inherits retry=3, timeout=30, namespace="notifications"
        let result = email_service::send(&input.to, &input.subject, &input.body).await?;
        Ok(EmailResult { message_id: result.id })
    }

    #[task(timeout = 10)]
    async fn send_sms(ctx: TaskContext, input: SmsInput) -> Result<SmsResult> {
        // overrides timeout=10, inherits retry=3, namespace="notifications"
        let result = twilio::send_sms(&input.phone, &input.message).await?;
        Ok(SmsResult { sid: result.sid })
    }

    #[task(retry = 5, timeout = 120, preset = "long-running")]
    async fn send_push(ctx: TaskContext, input: PushInput) -> Result<PushResult> {
        // fully custom: retry=5, timeout=120, preset="long-running"
        let result = fcm::send(&input.device_token, &input.payload).await?;
        Ok(PushResult { success: result.success })
    }

    // Not a task — plain helper preserved as-is
    fn build_template(template_name: &str, vars: &HashMap<String, String>) -> String {
        // Template rendering logic
        format!("rendered: {}", template_name)
    }
}
```

**Using in workflows:**

```rust
#[workflow]
async fn order_confirmation(ctx: WorkflowContext, order: Order) -> Result<()> {
    // Type-safe associated constants — compile error if task doesn't exist
    ctx.execute_task(NotificationTasks::send_email, EmailInput {
        to: order.email.clone(),
        subject: "Order Confirmed".to_string(),
        body: format!("Order #{} confirmed", order.id),
    }).await?;

    if let Some(phone) = &order.phone {
        ctx.execute_task(NotificationTasks::send_sms, SmsInput {
            phone: phone.clone(),
            message: format!("Order #{} confirmed!", order.id),
        }).await?;
    }

    Ok(())
}
```

**Group-level attributes reference:**

| Attribute | Type | Description |
|-----------|------|-------------|
| `retry` | `u32` | Max retry attempts (exponential backoff) |
| `timeout` | `u64` | Timeout in seconds |
| `timeout_mins` | `u64` | Timeout in minutes |
| `task_queue` | `String` | Task queue for routing |
| `namespace` | `String` | Namespace for multi-tenancy |
| `memory` | `String` | Memory requirement (e.g., `"512Mi"`) |
| `preset` | `String` | `"long-running"`, `"quick"`, or `"critical"` |
| `heartbeat_timeout` | `u64` | Heartbeat timeout in seconds |
| `priority` | `u8` | Priority 0-100 |
| `max_concurrent` | `u32` | Max concurrent executions |
| `rate_limit` | `u32` | Max executions per second |

### Task Context

The `TaskContext` is a crucial object passed to every task that provides access to workflow metadata, execution state, and utilities for long-running operations.

**What TaskContext Provides:**

1. **Workflow Identification** - Access to workflow ID, run ID, and task ID
2. **Execution Metadata** - Current attempt number, retry information
3. **Heartbeat Mechanism** - Signal progress for long-running tasks
4. **Cancellation Signals** - Detect when workflow/task is being cancelled
5. **Logging Context** - Structured logging with workflow context

**When to Use TaskContext:**

- **Always** available in task functions, even if you don't use it
- **Required** for heartbeats in long-running tasks
- **Useful** for debugging (include workflow_id in logs)
- **Essential** for cancellation-aware operations

Every task receives a `TaskContext` parameter. Let's explore what information is available:

**Core Properties:**

  // Unique ID for this task execution

  // Current attempt number (starts at 1)

  // Functions

  heartbeat(): Promise<void>;
  heartbeatWithDetails(details?: any): Promise<void>;
  isCancelled(): boolean;
}

**Why Metadata Matters:**

- **Debugging:** When a task fails, logs with `workflow_id` let you trace the entire workflow execution
- **Monitoring:** Track retry patterns by logging `attempt` numbers
- **Alerting:** Send alerts when tasks repeatedly fail (check `attempt` vs `maxAttempts`)
- **Audit Trail:** Include `workflow_id` in external API calls for end-to-end tracing
- **Dynamic Logic:** Adjust behavior based on attempt number (e.g., use fallback on final attempt)

**Real-World Example:**

```typescript
// Inside a @Tasks() class:
@Task({ name: 'processPayment' })
async processPayment(
  ctx: TaskContext,
  payment: Payment
): Promise<PaymentResult> {
  const workflowId = ctx.workflowId();
  const attempt = ctx.attempt();
  // Mirror the task's configured retryPolicy.maxAttempts
  const maxAttempts = 3;

  try {
    // Primary payment processor
    const result = await stripeClient.charge({
      amount: payment.amount,
      // Include workflow_id for traceability
      metadata: { workflowId },
    });

    return result;
  } catch (error) {
    // On final attempt, try backup processor
    if (attempt >= maxAttempts) {
      logger.warn('Stripe failed, trying PayPal as fallback', {
        workflowId,
        error: error.message,
      });

      return await paypalClient.charge({
        amount: payment.amount,
        metadata: { workflowId },
      });
    }

    throw error; // Let Orcher retry with Stripe
  }
}
```

### Heartbeats

**What are Heartbeats?**

Heartbeats are periodic signals sent from long-running tasks to indicate they're still making progress. Without heartbeats, Orcher might think a task is stuck and cancel it.

**When to Use Heartbeats:**

- Tasks that take **>30 seconds** to complete
- Tasks processing large batches (thousands of items)
- Tasks with unpredictable execution time
- Tasks that might appear "stuck" but are actually working

for (i, item) in items.iter().enumerate() {
    // Process item
    let processed = process_item(item).await?;
    results.push(processed);

    // Send heartbeat every 10 items
    if i % 10 == 0 {
        ctx.heartbeat().await?;
    }
}

}

### Heartbeats with Progress

You can include progress data with each heartbeat to track how far a task has progressed. This is useful for long-running tasks like file processing or batch jobs where you want to report completion percentage or the current item being processed.

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="language"
>

<TabPanel id="rust" label="Rust">

```rust
use serde::Serialize;

#[derive(Serialize)]
struct Progress {
current: usize,
total: usize,
percent: f64,
}

#[task(name = "process_with_progress")]
pub async fn process_with_progress(
ctx: TaskContext,
items: Vec<Item>,
) -> Result<ProcessedResult> {
let total = items.len();

for (current, item) in items.iter().enumerate() {
    process_item(item).await?;

    // Send heartbeat with progress details
    let progress = Progress {
        current: current + 1,
        total,
        percent: ((current + 1) as f64 / total as f64) * 100.0,
    };

    ctx.heartbeat_with_details(Some(progress)).await?;
}

Ok(ProcessedResult { count: total })
}
```

### Cancellation Handling

Tasks can detect cancellation requests and perform cleanup before exiting. Check for cancellation periodically in long-running tasks to release resources, close connections, or roll back partial work.

#[task(name = "cancellable_task")]
pub async fn cancellable_task(
ctx: TaskContext,
items: Vec<Item>,
) -> Result<ProcessedResult> {
for item in items {
    // Check for cancellation before processing
    if ctx.is_cancelled() {
        tracing::info!("Task cancelled, cleaning up...");
        cleanup().await?;
        return Err(anyhow::anyhow!("Task cancelled"));
    }

    process_item(item).await?;
}

Ok(ProcessedResult::success())
}

// Using cancellation token with tokio::select
#[task(name = "long_wait_task")]
pub async fn long_wait_task(
ctx: TaskContext,
duration_secs: u64,
) -> Result<String> {
let work = async {
    tokio::time::sleep(Duration::from_secs(duration_secs)).await;
    Ok("Work completed".to_string())
};

tokio::select! {
    result = work => result,
    _ = ctx.cancellation_token().cancelled() => {
        Err(anyhow::anyhow!("Task was cancelled"))
    }
}
}
