A workflow is defined using language-specific decorators or macros and receives a **workflow context** (`ctx`) that provides all the durable operations. The context is how you tell Orcher "this is a step that should be journaled."

```rust
use orcher::prelude::*;
use anyhow::Result;

// Define a workflow with the #[workflow] macro
#[workflow(
    name = "greet_user",
    version = "1.0.0",
    description = "Greet a user by name"
)]
pub async fn greet_user(
    ctx: WorkflowContext,
    name: String,
) -> Result<String> {
    // Step 1: Format greeting (type-safe task reference, automatically journaled)
    let greeting: String = ctx
        .execute_task(format_greeting, name.clone())
        .await?;

    // Step 2: Log the greeting (automatically journaled)
    ctx.execute_task(log_greeting, greeting.clone()).await?;

    // Return result
    Ok(greeting)
}

// Task: Format greeting
#[task(
    name = "format_greeting",
    description = "Format a greeting message"
)]
pub async fn format_greeting(_ctx: TaskContext, name: String) -> Result<String> {
    Ok(format!("Hello, {}!", name))
}

// Task: Log greeting
#[task(
    name = "log_greeting",
    description = "Log the greeting message"
)]
pub async fn log_greeting(_ctx: TaskContext, message: String) -> Result<()> {
    println!("Greeting: {}", message);
    Ok(())
}
```

**Start the workflow:**

```rust

    let result: String = handle.result().await?;
```

```typescript
  @Task({ name: 'log_greeting' })

// Define a workflow with the @Workflow decorator
@Workflow({ name: 'greet_user', version: '1.0' })

    const greeting = await ctx.executeTask(
      greetingTasks.formatGreeting,
      { name: input.name }
    );

    // Step 2: Log the greeting (automatically journaled)
    await ctx.executeTask(greetingTasks.logGreeting, { message: greeting });

    // Return result
    return greeting;
  }
}
```

In this example, `greet_user` is the workflow and `format_greeting` / `log_greeting` are tasks. The workflow orchestrates the tasks in sequence. Each `execute_task` call is a journaled step — if the workflow crashes after formatting the greeting but before logging it, the replay will skip the formatting step (using the journaled result) and only execute the logging step.

## How Workflows Work

### The Execution Model

When your workflow code calls `ctx.execute_task()` (or any other context method), the following happens under the hood:

1. **Journal check** — The system checks whether this step has already been executed by looking up the step's sequence number in the journal. Each context call in your workflow gets a deterministic sequence number based on its position in the execution flow.

2. **First execution** — If the step is not in the journal, the task is dispatched to a worker, executed, and the result is written to the journal in PostgreSQL. The workflow then receives the result and continues.

3. **Replay** — If the step is already in the journal (because the workflow is being replayed after a crash), the journaled result is returned immediately without executing the task again. From your workflow code's perspective, the call looks identical — it `await`s and gets back the same result.

This is the key insight: **your workflow function runs from the beginning every time**, but completed steps are fast-forwarded using journaled results. The function itself is the source of truth for the execution order; the journal is the source of truth for the results.

### Journaling in Action

Here's what happens when a payment workflow executes, crashes, and recovers:

    { step: 3, task: 'send_confirmation', status: 'crashed' },
  ]}

    { step: 1, task: 'charge_card', result: '"ch_123"', status: 'cached' },
    { step: 2, task: 'reserve_inventory', result: '"ok"', status: 'cached' },
    { step: 3, task: 'send_confirmation', status: 'fresh' },
  ]}
/>

Notice that `charge_card` is not called a second time. On replay the customer is not charged again: the charge ran during the first execution, and its journaled result (`ch_123`) is returned instead of calling the API. This is how Orcher avoids repeating completed work on replay. If a task fails _before_ its result is recorded, it will be retried — so make external calls idempotent.

## Workflow Context

The `WorkflowContext` (called `ctx` by convention) is the interface between your workflow code and the Orcher runtime. Every method on the context represents a **durable operation** — one that is journaled and safe to replay. You should never perform side effects (API calls, database writes, file I/O) directly in workflow code. Instead, execute them through the context.

Orcher provides two ways to execute work inside a workflow: **`execute_task`** for distributed, registered tasks and **`execute`** for inline, one-off operations. Both are journaled and replay-safe, but they differ in how and where the work runs.

### execute_task — Distributed Task Execution

`execute_task` is the primary way workflows interact with the outside world. It references a **registered task** — a function decorated with `@task` (Python), `#[task]` (Rust), or `@Task` (TypeScript) — and schedules it for **distributed execution** via a task queue.

When you call `execute_task`:

1. The workflow emits a `ScheduleTask` command and **suspends**
2. The task is placed on a task queue and picked up by a **task worker** (which may be a different process or machine)
3. The worker executes the task function and records the result
4. The workflow is re-dispatched, replays to the suspension point, and receives the result

This distributed model means tasks scale independently from workflows. You can run 10 workflow workers and 100 task workers, or vice versa.

`execute_task` also supports rich configuration: retry policies, timeouts, and heartbeat monitoring — all defined at the task level.

#### Type-Safe Task References

Orcher strongly encourages **type-safe task references** across all SDKs. Instead of passing a string task name to `execute_task`, you pass a **typed reference** to the task itself. This gives you:

- **Compile-time / import-time validation** — A misspelled task name is caught by the compiler (Rust) or at import time (TypeScript/Python), not at runtime in production.
- **Input/output type inference** — The SDK knows what input a task expects and what output it returns. Pass the wrong shape and your IDE or compiler tells you immediately.
- **IDE support** — Autocomplete, go-to-definition, and rename refactoring all work because task references are real code symbols, not opaque strings.
- **Zero runtime overhead** — In Rust, the `#[task]` macro generates a zero-sized const that resolves to a `&'static str` at compile time. In TypeScript, `createTaskRefs()` is a type-level cast with no runtime cost. In Python, the decorated function itself carries metadata.

Each SDK implements this differently, but the principle is the same: **reference the task, not its name**.

In Rust, the `#[task]` macro generates a type-safe const with the same name as your function. You pass this const (not a string) to `execute_task`, so the compiler catches typos and enforces input/output types.

```rust
use orcher::prelude::*;
use anyhow::Result;

// Define a registered task
#[task(name = "charge_card", timeout = 60, retry = 3)]
pub async fn charge_card(
    _ctx: TaskContext,
    amount: f64,
    card_token: String,
) -> Result<ChargeResult> {
    // This runs on a task worker (potentially a different machine)
    stripe::Charge::create(&client, amount, &card_token).await
}

#[workflow(name = "process_payment", version = "1.0.0")]
pub async fn process_payment(
    ctx: WorkflowContext,
    input: PaymentInput,
) -> Result<PaymentOutput> {
    // Type-safe task reference — compiler catches typos
    let charge: ChargeResult = ctx
        .execute_task(charge_card, (input.amount, input.card_token.clone()))
        .await?;

    // If workflow crashes here, charge_card won't be re-executed on replay

    let inventory: InventoryResult = ctx
        .execute_task(reserve_inventory, input.order_id.clone())
        .await?;

    Ok(PaymentOutput {
        charge_id: charge.charge_id,
        reserved: inventory.reserved,
    })
}
```

### execute — Inline Closure Execution

`execute` runs an inline closure (an anonymous function) **directly in the workflow's process** and journals the result. Unlike `execute_task`, there is no task queue, no distributed scheduling, and no separate worker. The closure executes immediately, its result is recorded, and on replay the journaled result is returned without re-executing the closure.

Use `execute` when:
- You need a **one-off operation** that doesn't warrant defining a reusable registered task
- You want to make an **API call, database query, or computation** replay-safe without the overhead of task scheduling
- The operation is **specific to this workflow** and won't be reused elsewhere

`execute` takes two arguments: a **step name** (a string used as the journal key) and an **async closure** that returns the result. The step name must be unique within the workflow.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[workflow(name = "order_workflow", version = "1.0.0")]
pub async fn order_workflow(
    ctx: WorkflowContext,
    user_id: u64,
) -> Result<OrderSummary> {
    // Inline closure — runs directly, no task queue
    let user: User = ctx
        .execute("fetch_user", move || async move {
            // This runs in the workflow's process, not a task worker
            let response = reqwest::get(format!("https://api.example.com/users/{}", user_id)).await?;
            Ok(response.json().await?)
        })
        .await?;

    // Another inline operation
    let orders: Vec<Order> = ctx
        .execute("fetch_orders", move || async move {
            let response = reqwest::get(format!("https://api.example.com/users/{}/orders", user_id)).await?;
            Ok(response.json().await?)
        })
        .await?;

    // Pure computation — also safe to journal
    let total: f64 = ctx
        .execute("calculate_total", {
            let orders = orders.clone();
            move || async move {
                Ok(orders.iter().map(|o| o.amount).sum())
            }
        })
        .await?;

    Ok(OrderSummary { user, orders, total })
}
```

### Choosing Between execute_task and execute

Both methods are journaled and replay-safe. The difference is **where** and **how** the work runs:

| | `execute_task` | `execute` |
|---|---|---|
| **Execution** | Distributed — runs on a task worker via a task queue | Inline — runs directly in the workflow's process |
| **Task definition** | Requires a registered task (`@task` / `#[task]` / `@Task`) | No registration — pass any async closure |
| **Type safety** | Full — typed task references enforce input/output types at compile time | Manual — you choose the step name string and closure return type |
| **Retry policies** | Configurable (max attempts, backoff, timeouts) | None — closure exceptions propagate directly |
| **Scaling** | Task workers scale independently from workflow workers | Scales with the workflow worker |
| **Reusability** | Task can be called from multiple workflows | Closure is specific to this workflow |
| **Best for** | API calls, database writes, long-running operations, reusable work | One-off queries, quick computations, workflow-specific operations |

In practice, most workflows use a mix of both. Use `execute_task` for operations that need retry policies, independent scaling, or reuse across workflows. Use `execute` for one-off operations that are specific to a single workflow.

### Execute Child Workflows

Workflows can start and wait on other workflows. This is called **workflow composition** and is how you break complex processes into smaller, reusable pieces. The parent workflow blocks until the child completes, and the child's result is journaled in the parent's journal. If the parent replays, the child's result is replayed from the journal — the child is not re-executed.

Child workflows run independently — they have their own journal, their own retry behavior, and can run on different workers. If the parent crashes, the child continues running. When the parent replays and reaches the child workflow step, it waits for the already-running child to complete (or replays the result if the child already finished).

### Durable Timers

`ctx.sleep()` pauses the workflow for a specified duration without holding any resources. Unlike `thread::sleep` or `time.sleep`, a durable timer **survives server restarts**. When you call `ctx.sleep(1 hour)`, the workflow releases its worker, and the server schedules a timer in the database. An hour later, the timer fires and the workflow is re-dispatched to a worker to continue.

This makes durable timers suitable for delays of any length — minutes, hours, or days. The workflow consumes zero resources while waiting.

```rust
    ctx: WorkflowContext,
    delay_seconds: u64,

    // Durable timer (survives restarts)
    ctx.sleep(Duration::from_secs(delay_seconds)).await?;

    // Send reminder after delay
    ctx.execute_task(send_reminder, ()).await?;

    Ok(())
}
```

### Wait for Events

`ctx.wait_for_event()` pauses the workflow until an external event arrives or a timeout expires. This is how workflows implement **human-in-the-loop** patterns like approval flows, payment confirmations, or webhook callbacks.

Like durable sleep, waiting for an event releases the worker. The workflow is suspended — consuming no resources — until either the event is delivered (via the `send_event` API) or the timeout is reached.

Events are identified by name. When an external system calls `send_event("approval", payload)` targeting this workflow, the payload is written to the workflow's journal and the workflow is re-dispatched to a worker. On replay, the workflow fast-forwards to the `wait_for_event` call and returns the journaled payload immediately.

```rust
use orcher::prelude::*;
use anyhow::Result;
use std::time::Duration;

#[workflow(
    name = "approval_workflow",
    version = "1.0.0"
)]
pub async fn approval_workflow(
    ctx: WorkflowContext,
    request_id: String,
) -> Result<String> {
    // Wait for approval event (max 24 hours)
    let event: Option<ApprovalEvent> = ctx
        .wait_for_event_with_timeout("approval", Duration::from_secs(86400))
        .await?;

    match event {
        Some(e) if e.approved => {
            ctx.execute_task(process_approval, request_id).await?;
            Ok("Approved".to_string())
        }
        _ => Ok("Rejected".to_string()),
    }
}
```

### Send Events

Workflows can send events to other workflows. This enables **workflow-to-workflow communication** — for example, a payment workflow notifying an order workflow that payment succeeded. Sent events are journaled — on replay, the event is not re-sent, preventing duplicate notifications.

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
  <TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;
use anyhow::Result;

#[workflow(
    name = "order_workflow",
    version = "1.0.0"
)]
pub async fn order_workflow(
    ctx: WorkflowContext,
    order_id: String,
    notification_workflow_id: String,
) -> Result<()> {
    // Process order
    ctx.execute_task(process_order, order_id.clone()).await?;

    // Send event to another workflow when complete
    // The target workflow can receive this via wait_for_event("order_completed")
    ctx.send_event(
        &notification_workflow_id,
        "order_completed",
        serde_json::json!({ "order_id": order_id }),
    ).await?;

    Ok(())
}
```
