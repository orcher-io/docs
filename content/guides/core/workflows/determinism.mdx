Workflow code must be **deterministic**: given the same journal, it must ask for the same steps in the same order.

The reason is replay. A worker does not keep a workflow in memory while it waits. Each time there is something new for a run (a task finished, a timer fired, an event arrived), a worker runs the workflow function again from the top. Each step the function asks for is matched, in order, against the journal: a step that is already there returns its recorded result at once, and the first step that is not there is the new work. If the function asks for a different step than the one the journal holds at that position, the two no longer match and the run cannot go on.

## What is safe

- **Pure computation.** Arithmetic, string handling, building and transforming data.
- **Steps taken through the workflow context.** Running a task, sleeping, waiting for an event, starting a child workflow. Each is journaled.
- **Branching on a journaled value.** An `if` on a task's result takes the same branch on every replay, because the result comes from the journal.
- **The context's clock and random source.** See below.

## What is not safe

Anything that can give a different answer the next time the function runs:

| Not in workflow code | Use instead |
| --- | --- |
| The system clock | The workflow context's clock |
| Random numbers and UUIDs from the language or the OS | The workflow context's random source |
| Network calls, file and database access | A task |
| Environment variables, configuration read at run time, global state that changes | Pass the value in the workflow's input, or read it in a task |
| Iterating a collection whose order is not fixed, when the order decides which steps run | Sort it first |

## Time and randomness

You do not need a task to read the time or draw a random value. Each SDK gives the workflow context a clock and a random source that return the same values on every replay.

- **The clock is read from the journal.** It starts at the moment the engine journaled the workflow's start and moves forward each time the workflow receives something it waited for. It does not move while your code runs between those points.
- **The random source is seeded per run.** It draws the same sequence on every replay.

## When the rule is broken

A worker that replays a run and finds the code asking for something the journal does not hold detects it. It logs that the workflow "is not deterministic", does not apply the result, and hands the run back.

The run is **not failed**. It stays open, and workers keep trying it with a growing delay of up to a minute. It finishes as soon as a worker whose code matches the journal picks it up. You can also cancel or terminate it.

In practice this shows up in two ways:

- **A bug in the code**, such as a branch on the system clock. Fix the code so that it takes the path the journal recorded, and deploy it. The open runs then carry on.
- **A deploy that changed the steps** while runs were open. The code is deterministic, but it is no longer the code that wrote those journals. [Changing workflow code while runs are open](/guides/core/guarantees#changing-workflow-code-while-runs-are-open) says which changes are safe and how to make the ones that are not.
