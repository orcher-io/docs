Orcher is a **durable execution engine** — it makes your code survive failures automatically. You write normal functions, and Orcher records each step's result to PostgreSQL as it runs. If a process crashes, another worker picks up the execution and replays completed steps from the saved results without re-executing them.

- **Automatic checkpointing** — Every task result is saved before being returned to your workflow
- **Crash recovery** — Any worker can resume any workflow from its last checkpoint
- **No duplicate side effects** — Completed tasks return cached results on replay
- **Complete audit trail** — The journal records every step, its result, and when it happened

---

## The Problem Orcher Solves

Traditional code execution is ephemeral. When your process crashes, you lose all in-memory state, your position in the execution flow, and any partial results:

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
<TabPanel id="rust" label="Rust">

```rust
// Without Orcher — loses state on crash
async fn process_order(order: Order) -> Result<()> {
    let payment = charge_card(order.total).await?;      // ← Succeeds
    update_inventory(&order.items).await?;               // ← Succeeds
    send_confirmation_email(&order.email).await?;        // ← CRASHES HERE
    notify_warehouse(&order.id).await?;                  // ← Never runs

    // Customer was charged but never got confirmation.
    // You don't know which steps completed. No automatic way to resume.
    Ok(())
}
```

With Orcher, every step is journaled. After a crash, the workflow resumes from the first incomplete step:

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
<TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;

#[workflow(name = "process_order")]
async fn process_order(ctx: WorkflowContext, order: Order) -> Result<OrderResult> {
    let payment = ctx.execute_task("charge_card", order.total).await?;       // Journaled
    ctx.execute_task("update_inventory", &order.items).await?;               // Journaled
    ctx.execute_task("send_confirmation", &order.email).await?;              // Journaled
    ctx.execute_task("notify_warehouse", &order.id).await?;                  // Journaled

    // If crash happens after step 2, next run:
    // - charge_card: returns cached result (no duplicate charge)
    // - update_inventory: returns cached result
    // - send_confirmation: executes for the first time
    // - notify_warehouse: executes next
    Ok(OrderResult { order_id: order.id, payment_id: payment.id })
}
```

## Core Concepts

### Workflows

A workflow is a durable function that orchestrates tasks into a business process. It defines the order of operations, makes decisions, and handles errors — but never performs I/O directly. All external work is delegated to **tasks**.

Workflow code must be **deterministic** — given the same inputs and task results, it always follows the same execution path. This is what makes replay work. I/O operations are non-deterministic (they can return different results each time), so they must go through tasks whose results are cached in the journal.

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
<TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;

#[workflow(name = "onboard_customer")]
async fn onboard_customer(ctx: WorkflowContext, customer: NewCustomer) -> Result<OnboardResult> {
    // Workflows make decisions
    if customer.tier == "enterprise" {
        ctx.execute_task("assign_account_manager", &customer.id).await?;
    }

    // Workflows orchestrate tasks
    let account_id = ctx.execute_task("create_account", &customer).await?;
    ctx.execute_task("send_welcome_email", &customer.email).await?;
    ctx.execute_task("provision_resources", &account_id).await?;

    // Workflows handle errors with compensation
    match ctx.execute_task("charge_setup_fee", &customer.payment_method).await {
        Ok(_) => {}
        Err(e) => {
            ctx.execute_task("delete_account", &account_id).await?;
            return Err(e);
        }
    }

    Ok(OnboardResult { account_id, status: "active".into() })
}
```

**Workflows should:**
- Orchestrate tasks — decide which tasks to run and in what order
- Make decisions — branch logic based on task results
- Handle errors — catch task failures and run compensation tasks
- Coordinate systems — chain tasks that talk to different services

**Workflows should NOT:**
- Perform I/O directly — network calls, file reads, database queries must go through tasks
- Use non-deterministic functions — `Math.random()`, `Date.now()`, `Uuid::new_v4()` produce different values on replay; wrap them in tasks so the result is cached
- Store large data in workflow state — pass references (URLs, IDs) instead of large payloads

### Tasks

A task is a unit of work that performs one specific action — calling an API, writing to a database, or sending an email. Tasks are where all **side effects** happen. By isolating side effects in tasks, Orcher can cache their results for replay, retry them independently, and run them on different workers.

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
<TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;

#[task(name = "charge_card", timeout = 30, retry_policy(max_attempts = 3, backoff_coefficient = 2.0))]
async fn charge_card(ctx: TaskContext, input: ChargeInput) -> Result<ChargeResult> {
    let stripe = Stripe::new(&std::env::var("STRIPE_SECRET_KEY")?);

    let charge = stripe.charges().create(CreateCharge {
        amount: input.amount,
        currency: &input.currency,
        source: &input.payment_method,
        idempotency_key: Some(&input.idempotency_key),
        ..Default::default()
    }).await?;

    Ok(ChargeResult { charge_id: charge.id, status: charge.status })
}
```

**Task design principles:**

- **Idempotent** — Running the same task twice with the same input should produce the same result. Use idempotency keys for external APIs (e.g., Stripe). This matters because Orcher may retry tasks that fail partway through.
- **Focused** — One task, one action. "Charge the card" not "charge the card, update inventory, and send email." Smaller tasks mean more granular checkpoints.
- **Stateless** — Each invocation is independent. State across steps is managed by the workflow.
- **Serializable** — Input and output must be JSON-serializable (stored in PostgreSQL JSONB and sent over gRPC).

### Deterministic Replay

When a workflow resumes after a crash, it re-runs the entire workflow function from the beginning. Completed steps return cached results from the journal instantly. Because the same task results lead to the same decisions, the workflow follows the exact same execution path and reaches the point where the crash occurred.

This is why workflow code must be deterministic. If you use `Math.random()` directly in a workflow, the original run might take one branch and the replay might take a different branch, causing the replay to diverge from the journal. Anything non-deterministic must go inside a task:

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
<TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;

// BAD: Non-deterministic — different value on replay breaks journal alignment
#[workflow(name = "bad_workflow")]
async fn bad_workflow(ctx: WorkflowContext, input: Input) -> Result<Output> {
    let random: f64 = rand::random(); // Different each run!
    if random > 0.5 {
        ctx.execute_task("do_something", &input).await?;
    }
    Ok(Output {})
}

// GOOD: Random value captured in a task and cached in journal
#[workflow(name = "good_workflow")]
async fn good_workflow(ctx: WorkflowContext, input: Input) -> Result<Output> {
    let random: f64 = ctx.execute_task("generate_random", &()).await?;
    if random > 0.5 {
        ctx.execute_task("do_something", &input).await?; // Same branch on replay
    }
    Ok(Output {})
}
```

**Non-deterministic operations to avoid in workflows:**
- Random values — `Math.random()`, `rand::random()`, `random.random()`
- Current time — `Date.now()`, `Instant::now()`, `datetime.now()`
- UUID generation — `Uuid::new_v4()`, `crypto.randomUUID()`
- Direct I/O — HTTP requests, file reads, database queries
- Global mutable state — reading from variables that change between runs

**Orchestrator** — A stateless server (gRPC on port 50051, REST API on port 8080) that coordinates workflow execution, task scheduling, and worker polling. All state lives in PostgreSQL, so you can run multiple orchestrator instances for high availability.

**SDK Workers** — Your application processes running the Orcher SDK. Workers register with the orchestrator, poll for work via gRPC long-polling, execute your workflow and task handlers, and report results. Workers are stateless — if one crashes, another picks up the work.

**PostgreSQL** — The primary data store for workflow state, journal entries, task executions, and the work queue (`SELECT FOR UPDATE SKIP LOCKED`).

**Redis** (optional) — Wakes workers via `LPUSH`/`BRPOP` as soon as work is queued. Without Redis, the system falls back to PostgreSQL-based polling.

### Execution Flow

1. **Start workflow** — Your application calls the orchestrator's `StartWorkflowExecution` gRPC endpoint (or `POST /api/v1/workflows/execute` on the orchestrator's REST API). The orchestrator creates a workflow execution record in PostgreSQL.

2. **Worker polls** — SDK workers long-poll the orchestrator via `PollWorkflowExecution`. When work is available, the orchestrator assigns the workflow to a worker using `SELECT FOR UPDATE SKIP LOCKED`.

3. **Replay and execute** — The worker loads the journal from the orchestrator, replays completed steps (returning cached results), and executes the next pending step. Each `ctx.execute_task()` call schedules a task on the orchestrator.

4. **Task dispatch** — The orchestrator places the task on the worker's task queue. A worker polls via `PollTaskExecution`, executes the task handler, and reports the result via `CompleteTaskExecution`.

5. **Continue or complete** — After a task completes, the orchestrator re-queues the workflow for the next step. This repeats until the workflow finishes or fails.

## Compensation Pattern (Sagas)

When operations span multiple services, you can't use a single database transaction. Workflows solve this with compensation — if a later step fails, you run "undo" tasks for the steps that already succeeded:

<Tabs scrollable size="small" type="underlined" defaultActiveId="rust" queryGroup="language">
<TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;

#[workflow(name = "transfer_money")]
async fn transfer_money(ctx: WorkflowContext, transfer: Transfer) -> Result<TransferResult> {
    // Debit source account
    ctx.execute_task("debit_account", &DebitInput {
        account_id: transfer.from.clone(),
        amount: transfer.amount,
    }).await?;

    // Credit destination — if this fails, compensate
    match ctx.execute_task("credit_account", &CreditInput {
        account_id: transfer.to.clone(),
        amount: transfer.amount,
    }).await {
        Ok(_) => Ok(TransferResult { status: "completed".into() }),
        Err(e) => {
            // Refund the debit
            ctx.execute_task("refund_account", &RefundInput {
                account_id: transfer.from.clone(),
                amount: transfer.amount,
            }).await?;
            Err(e)
        }
    }
}
```

## When to Use Orcher

**Good fit:**
- **Multi-step business processes** — order processing, user onboarding, payment flows
- **Distributed transactions** — cross-service operations with compensation (Saga pattern)
- **Long-running operations** — data migrations, batch processing, report generation
- **External dependencies** — API integrations with retries, human approvals that take days
- **Critical operations** — financial transactions, data pipelines, compliance workflows

**Not ideal for:**
- **Real-time streaming** — use a stream processor; journaling every step adds latency a per-event stream may not afford
- **Simple CRUD** — direct database access is simpler when the operation is already atomic
- **Stateless HTTP APIs** — no orchestration needed if each request is independent
