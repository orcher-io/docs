The best way to understand journaling is to see it in action. The examples below show a payment workflow with three steps. On first execution, each step runs normally and its result is journaled. If the workflow crashes and replays, completed steps return their journaled result instantly — the external API calls never happen again.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[task]
pub async fn charge_card(_ctx: TaskContext, input: PaymentInput) -> Result<ChargeResult> {
    // Call Stripe API...
}

#[task]
pub async fn reserve_inventory(_ctx: TaskContext, order_id: String) -> Result<InventoryResult> {
    // Reserve stock...
}

#[task]
pub async fn send_confirmation(_ctx: TaskContext, charge_id: String) -> Result<()> {
    // Send email...
}

#[workflow]
pub async fn payment_workflow(
    ctx: WorkflowContext,
    order: OrderInput,
) -> Result<PaymentResult> {
    // Step 1: Charge card
    // First execution: Executes and journals result
    // Replay: Returns journaled result without re-executing
    let charge: ChargeResult = ctx
        .execute_task(charge_card, order.clone())
        .await?;

    // If crash happens here, step 1 is already journaled

    // Step 2: Reserve inventory
    // First execution: Executes and journals result
    // Replay: Returns journaled result
    let inventory: InventoryResult = ctx
        .execute_task(reserve_inventory, order.id.clone())
        .await?;

    // Step 3: Send confirmation
    // Always executes (not in journal yet)
    ctx.execute_task(send_confirmation, charge.id.clone()).await?;

    Ok(PaymentResult {
        charge_id: charge.id,
        reserved: inventory.reserved,
    })
}
```

### Two Storage Layers

| Layer | Table | Key | Purpose |
|-------|-------|-----|---------|
| **Execution Log** | `execution_log` | `(workflow_id, step_name)` | Step-level idempotency cache. Stores result, status, attempt count. Used for `ctx.execute()` replay protection. |
| **Journal** | `workflow_execution_journal` | `(workflow_id, execution_id, event_id)` | Append-only event history. Full audit trail. Provides the entries that drive replay via `journal_to_jobs()`. |

### In-Memory Cache (HighPerfCache)

Orcher uses a [Moka](https://github.com/moka-rs/moka)-based cache to avoid hitting PostgreSQL on every replay:

- **TTL**: 60 seconds per entry
- **Max entries**: 5,000 cached journals
- **Incremental loading**: On cache hit, only loads entries with `event_id > max_cached_event_id` (partial DB query instead of full reload)
- **Optimistic append**: When a new entry is written, it's appended to the in-memory cache immediately (no DB roundtrip to refresh)
- **Metrics**: `journal_hits`, `journal_misses`, `journal_hit_rate()` tracked for observability

| Field | Type | Description |
|-------|------|-------------|
| `id` | `BIGSERIAL` | Database primary key (auto-increment) |
| `workflow_id` | `VARCHAR` | User-facing workflow identifier |
| `execution_id` | `VARCHAR` | Unique execution/run identifier |
| `event_id` | `BIGINT` | Monotonically increasing sequence within the execution — determines replay order |
| `event_type` | `VARCHAR` | Event type (`StepCompleted`, `EventReceived`, `TimerFired`, etc.) |
| `timestamp` | `TIMESTAMPTZ` | When the event occurred |
| `payload` | `JSONB` | Event payload — step results, failure details, event data |
| `version` | `INTEGER` | Schema version for evolution |
| `task_id` | `BIGINT` | Associated task ID (0 if not task-related) |
| `organization_id` | `UUID` | Multi-tenancy support |
| `shard_id` | `INTEGER` | Horizontal sharding partition |
| `created_at` | `TIMESTAMPTZ` | When journal entry was inserted |

**Uniqueness constraint**: `(workflow_id, execution_id, event_id)` — prevents duplicate events within an execution.

## Journal Entry Types

Orcher records different types of entries throughout workflow execution:

### Step Events

Step events track the completion of individual operations within a workflow. These are the most common entry type and drive the replay mechanism.

- `StepCompleted` — A step finished (inline closure, distributed task, child workflow, or side effect). This is the primary entry type that drives replay.

### Workflow Lifecycle

These events mark the major state transitions of a workflow execution — from start through completion, failure, cancellation, or timeout.

- `WorkflowExecutionStarted` — Workflow begins execution
- `WorkflowExecutionCompleted` — Workflow completes successfully
- `WorkflowExecutionFailed` — Workflow fails with error
- `WorkflowExecutionCanceled` — Workflow is cancelled
- `WorkflowExecutionTimedOut` — Workflow exceeds timeout
- `WorkflowExecutionRestartedFresh` — Workflow restarted with clean state

### Task Events

Task events track the lifecycle of distributed tasks dispatched to task queues. These entries record when a task is scheduled, completes, fails, or is cancelled.

- `TaskScheduled` — Task dispatched to task queue
- `TaskCompleted` — Task completes successfully
- `TaskFailed` — Task fails with error
- `TaskCanceled` — Task is cancelled

### Signal and Event Events

Signal events record inter-workflow communication. These track when external events are delivered to a workflow or when a workflow sends a signal to another workflow.

- `EventReceived` — External signal/event delivered to workflow (data is base64-encoded in the payload field)
- `ExternalEventSent` — Workflow sent a signal to another workflow

### Child Workflow Events

Child workflow events track the full lifecycle of workflows spawned by a parent. These entries enable the parent to monitor and replay child workflow results.

- `ChildWorkflowExecutionInitiated` — Child workflow created
- `ChildWorkflowExecutionStarted` — Child workflow begins running
- `ChildWorkflowExecutionCompleted` — Child workflow completes
- `ChildWorkflowExecutionFailed` — Child workflow fails
- `ChildWorkflowExecutionTimedOut` — Child workflow exceeds timeout
- `ChildWorkflowExecutionCanceled` — Child workflow is cancelled

### Timer Events

Timer events record durable sleeps and delays within a workflow.

- `TimerFired` — Timer/sleep completes
