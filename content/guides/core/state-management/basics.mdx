## Setting and Getting State

The `WorkflowContext` provides `set_state()` and `get_state()` methods to store and retrieve typed values by string key. State values are JSON-serialized, so any serializable type can be stored.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[task]
pub async fn process_payment(_ctx: TaskContext, amount: f64) -> Result<PaymentResult> {
    // ...
}

#[workflow]
pub async fn order_workflow(
    ctx: WorkflowContext,
    input: OrderInput,
) -> Result<OrderResult> {
    // Set state values
    ctx.set_state("order_id", &input.order_id)?;
    ctx.set_state("status", &"processing")?;
    ctx.set_state("customer_id", &input.customer_id)?;

    // Process order
    let payment_result: PaymentResult = ctx
        .execute_task(process_payment, input.amount)
        .await?;

    // Update state after task completes
    ctx.set_state("payment_id", &payment_result.payment_id)?;
    ctx.set_state("status", &"paid")?;

    // Get state value
    let current_status: Option<String> = ctx.get_state("status")?;
    println!("Current status: {:?}", current_status);

    Ok(OrderResult {
        order_id: input.order_id,
        payment_id: payment_result.payment_id,
        status: current_status.unwrap_or_default(),
    })
}
```

<TabPanel id="typescript" label="TypeScript">

```typescript
import { Workflow, Tasks, Task, WorkflowContext, TaskContext, createTaskRefs } from '@orcher/sdk';

@Tasks({ taskQueue: 'orders' })
class OrderTasks {
  @Task()
  async processPayment(ctx: TaskContext, amount: number): Promise<PaymentResult> {
    // ...
  }
}

const tasks = createTaskRefs(OrderTasks);

@Workflow()
class OrderWorkflow {
  async run(ctx: WorkflowContext, input: OrderInput): Promise<OrderResult> {
    // Set state values
    ctx.setState('orderId', input.orderId);
    ctx.setState('status', 'processing');
    ctx.setState('customerId', input.customerId);

    // Process order
    const paymentResult = await ctx.executeTask(tasks.processPayment, input.amount);

    // Update state after task completes
    ctx.setState('paymentId', paymentResult.paymentId);
    ctx.setState('status', 'paid');

    // Get state value
    const currentStatus = ctx.getState<string>('status');
    console.log('Current status:', currentStatus);

    return {
      orderId: input.orderId,
      paymentId: paymentResult.paymentId,
      status: currentStatus || '',
    };
  }
}
```

```python
from dataclasses import dataclass
from orcher import workflow, task, WorkflowContext, TaskContext


@dataclass
class OrderInput:
    order_id: str
    customer_id: str
    amount: float


@dataclass
class OrderResult:
    order_id: str
    payment_id: str
    status: str


@task(name="process_payment")
async def process_payment(ctx: TaskContext, amount: float) -> PaymentResult:
    ...


@workflow(name="order_workflow")
async def order_workflow(ctx: WorkflowContext, input: OrderInput) -> OrderResult:
    # Set state values
    ctx.set_state("order_id", input.order_id)
    ctx.set_state("status", "processing")
    ctx.set_state("customer_id", input.customer_id)

    # Process order
    payment_result = await ctx.execute_task(process_payment, amount=input.amount)

    # Update state after task completes
    ctx.set_state("payment_id", payment_result.payment_id)
    ctx.set_state("status", "paid")

    # Get state value
    current_status = ctx.get_state("status")
    print(f"Current status: {current_status}")

    return OrderResult(
        order_id=input.order_id,
        payment_id=payment_result.payment_id,
        status=current_status or "",
    )
```

## State Lifecycle

### State Persistence

State is stored in-memory during workflow execution and reconstructed from the journal on replay. This means state values set before a crash are available after the workflow resumes — the replay re-executes the workflow code, and `set_state()` calls run again with the same deterministic values.

1. **After `set_state()` calls** — Value is stored in the in-memory state map
2. **After task completions** — The completed task result is journaled; on replay, the same result is returned and the subsequent `set_state()` calls produce identical state
3. **On crash/restart** — The journal is replayed, reconstructing the same state
4. **During replay** — `set_state()` calls execute normally but produce the same values because the workflow is deterministic

### State During Replay

The diagram below shows how state is consistent across first execution and replay. Since workflows are deterministic and task results are journaled, every `set_state()` call produces the same value on replay.
