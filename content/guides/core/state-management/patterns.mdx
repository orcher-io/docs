## Common State Patterns

These patterns demonstrate how to use workflow state for real-world scenarios. Each example shows how state enables progress tracking, status transitions, and result accumulation across long-running workflows.

### Progress Tracking

Track how far a batch workflow has progressed. External systems can query the progress state to display completion percentage in a dashboard or UI.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[task]
pub async fn process_item(_ctx: TaskContext, item: Item) -> Result<ProcessedItem> {
    // ...
}

#[workflow]
pub async fn batch_processor(
    ctx: WorkflowContext,
    items: Vec<Item>,
) -> Result<BatchResult> {
    // Initialize progress state
    ctx.set_state("total_items", &items.len())?;
    ctx.set_state("processed_items", &0usize)?;
    ctx.set_state("failed_items", &0usize)?;
    ctx.set_state("status", &"running")?;

    let mut results = Vec::new();

    for (index, item) in items.iter().enumerate() {
        // Update progress
        ctx.set_state("current_item", &index)?;
        ctx.set_state("processed_items", &(index + 1))?;

        // Process item
        match ctx.execute_task(process_item, item.clone()).await {
            Ok(result) => {
                results.push(result);
            }
            Err(_e) => {
                let failed: usize = ctx.get_state("failed_items")?.unwrap_or(0);
                ctx.set_state("failed_items", &(failed + 1))?;
            }
        }

        // Calculate percentage
        let percentage = ((index + 1) as f64 / items.len() as f64) * 100.0;
        ctx.set_state("progress_percentage", &percentage)?;
    }

    ctx.set_state("status", &"completed")?;

    Ok(BatchResult {
        total: items.len(),
        processed: results.len(),
        failed: items.len() - results.len(),
    })
}
```

```typescript
import { Workflow, Tasks, Task, WorkflowContext, TaskContext, createTaskRefs } from '@orcher/sdk';

@Tasks({ taskQueue: 'processing' })
class ProcessingTasks {
  @Task()
  async processItem(ctx: TaskContext, item: Item): Promise<ProcessedItem> { /* ... */ }
}

const tasks = createTaskRefs(ProcessingTasks);

@Workflow()
class BatchProcessor {
  async run(ctx: WorkflowContext, items: Item[]): Promise<BatchResult> {
    // Initialize progress state
    ctx.setState('totalItems', items.length);
    ctx.setState('processedItems', 0);
    ctx.setState('failedItems', 0);
    ctx.setState('status', 'running');

    const results: ProcessedItem[] = [];

    for (let index = 0; index < items.length; index++) {
      // Update progress
      ctx.setState('currentItem', index);
      ctx.setState('processedItems', index + 1);

      // Process item
      try {
        const result = await ctx.executeTask(tasks.processItem, items[index]);
        results.push(result);
      } catch (error) {
        const failed = ctx.getState<number>('failedItems') || 0;
        ctx.setState('failedItems', failed + 1);
      }

      // Calculate percentage
      const percentage = ((index + 1) / items.length) * 100;
      ctx.setState('progressPercentage', percentage);
    }

    ctx.setState('status', 'completed');

    return {
      total: items.length,
      processed: results.length,
      failed: items.length - results.length,
    };
  }
}
```

```python
        ctx.set_state("progress_percentage", percentage)

    ctx.set_state("status", "completed")

    return BatchResult(
        total=len(items),
        processed=len(results),
        failed=len(items) - len(results),
```

### Status Machine

Model workflow execution as a state machine with well-defined transitions. Each phase of the workflow updates the status, making it easy to track where the workflow is at any point — and to resume from the correct phase after a crash.

```rust
use anyhow::Result;

#[derive(Serialize, Deserialize, Clone)]
enum OrderStatus {
    Created,
    PaymentProcessing,
    PaymentCompleted,
    Fulfilling,
    Shipped,
    Delivered,
    Failed,
}

#[task]
pub async fn process_payment(_ctx: TaskContext, order_id: String) -> Result<Payment> { /* ... */ }

#[task]
pub async fn fulfill_order(_ctx: TaskContext, order_id: String) -> Result<Fulfillment> { /* ... */ }

#[task]
pub async fn ship_order(_ctx: TaskContext, fulfillment_id: String) -> Result<Tracking> { /* ... */ }

#[workflow]
pub async fn order_fulfillment(
    ctx: WorkflowContext,
    order_id: String,
) -> Result<OrderResult> {
    // Initialize status
    ctx.set_state("status", &OrderStatus::Created)?;
    ctx.set_state("order_id", &order_id)?;

    // Payment phase
    ctx.set_state("status", &OrderStatus::PaymentProcessing)?;
    let payment = ctx.execute_task(process_payment, order_id.clone()).await?;
    ctx.set_state("status", &OrderStatus::PaymentCompleted)?;
    ctx.set_state("payment_id", &payment.payment_id)?;

    // Fulfillment phase
    ctx.set_state("status", &OrderStatus::Fulfilling)?;
    let fulfillment = ctx.execute_task(fulfill_order, order_id.clone()).await?;
    ctx.set_state("fulfillment_id", &fulfillment.fulfillment_id)?;

    // Shipping phase
    ctx.set_state("status", &OrderStatus::Shipped)?;
    let tracking = ctx.execute_task(ship_order, fulfillment.fulfillment_id).await?;
    ctx.set_state("tracking_number", &tracking.tracking_number)?;

    // Delivery
    ctx.set_state("status", &OrderStatus::Delivered)?;

    Ok(OrderResult {
        order_id,
        status: "delivered".to_string(),
    })
}
```

### Accumulating Results

Collect results from multiple steps into aggregate state. This pattern is useful for fan-out workflows where you process data from multiple sources and need to track totals across iterations.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[task]
pub async fn fetch_from_source(_ctx: TaskContext, source: DataSource) -> Result<SourceData> {
    // ...
}

#[workflow]
pub async fn data_aggregation(
    ctx: WorkflowContext,
    sources: Vec<DataSource>,
) -> Result<AggregateResult> {
    // Initialize aggregation state
    ctx.set_state("total_records", &0usize)?;
    ctx.set_state("total_bytes", &0usize)?;
    ctx.set_state("sources_completed", &0usize)?;

    let mut all_data = Vec::new();

    for source in sources {
        // Fetch data from source
        let data: SourceData = ctx
            .execute_task(fetch_from_source, source)
            .await?;

        // Accumulate results
        all_data.extend(data.records);

        // Update aggregate state
        let total_records: usize = ctx.get_state("total_records")?.unwrap_or(0);
        let total_bytes: usize = ctx.get_state("total_bytes")?.unwrap_or(0);
        let sources_completed: usize = ctx.get_state("sources_completed")?.unwrap_or(0);

        ctx.set_state("total_records", &(total_records + data.records.len()))?;
        ctx.set_state("total_bytes", &(total_bytes + data.size_bytes))?;
        ctx.set_state("sources_completed", &(sources_completed + 1))?;
    }

    Ok(AggregateResult {
        total_records: all_data.len(),
        total_bytes: ctx.get_state("total_bytes")?.unwrap_or(0),
    })
}
```

## Querying Workflow State

External systems can query workflow state without blocking execution. Workflows register query handlers that return state values on demand — clients call `query_workflow()` with a query name, and the handler runs inside the workflow context with access to the current state.

### Registering Query Handlers

Define query handlers inside your workflow to expose state to external callers. Each handler has a name and returns a serializable value.

```rust
pub async fn order_workflow(
    ctx: WorkflowContext,
    input: OrderInput,
) -> Result<OrderResult> {
    ctx.set_state("status", &"processing")?;

    ctx.register_query_handler("get_status", || {
```

## State vs Variables

Understanding when to use workflow state vs. local variables helps you write efficient workflows. Use state for values that need to survive crashes or be queried externally. Use local variables for temporary computations that can be cheaply recomputed on replay.

### Use Workflow State When:

- **Need persistence** — Value must survive crashes and be consistent on replay
- **External queries** — Value needs to be queried by external systems via query handlers
- **Progress tracking** — Monitoring workflow execution from a dashboard or API
- **Long-running workflows** — Workflow runs for hours/days and needs observable state

### Use Local Variables When:

- **Temporary computation** — Only needed within a single code block
- **Derived values** — Can be recomputed from task results on replay
- **Performance critical** — Avoid serialization overhead for hot-path values
- **Private data** — Should not be externally queryable

```rust
#[workflow]
pub async fn example_workflow(
    ctx: WorkflowContext,
    input: Input,
) -> Result<Output> {
    // State: Needs to survive crash and be queryable
    ctx.set_state("order_id", &input.order_id)?;

    // Local variable: Temporary computation, recomputed on replay
    let tax = input.amount * 0.08;
    let total = input.amount + tax;

    // State: Progress tracking (queryable by external systems)
    ctx.set_state("status", &"processing")?;

    let result = ctx.execute_task(process, total).await?;

    // Local variable: Derived from task result
    let formatted = format!("Result: {}", result);

    // State: Final result (queryable)
    ctx.set_state("result", &result)?;

    Ok(Output { result })
}
```

```python
    # Local variable: Derived from task result
    formatted = f"Result: {result}"

    # State: Final result (queryable)
    ctx.set_state("result", result)

    return Output(result=result)
```
