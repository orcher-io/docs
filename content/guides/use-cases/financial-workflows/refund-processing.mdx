Refunds are their own workflow — they need to reverse the original charge, return inventory to stock, update the accounting ledger, and notify the customer. By modeling refunds as a separate workflow, you get independent retry logic, a dedicated audit trail, and the ability to handle partial refunds.

Don't confuse this with the `refund_charge` compensation in [payment processing](/guides/use-cases/financial-workflows/payment-processing) — that's an immediate undo inside a payment that's still failing. This is a business process in its own right, usually started days later by a support tool or customer portal:

## How it works

The four steps run in a deliberate order: the only step that can be *declined* goes first, and the bookkeeping that must never diverge from the money follows it.

That inevitability is the point. The failure mode this design eliminates is *divergence*: a refund issued at the gateway that never reaches the ledger. If the gateway refuses the refund, nothing was recorded anywhere; once it succeeds, the journaled `refund_id` guarantees the remaining bookkeeping runs to completion — a crash can delay the ledger entry, but it can never lose it.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[derive(Debug, Clone, Serialize, Deserialize)]
struct RefundRequest {
    order_id: String,
    charge_id: String,
    amount: f64,        // Full or partial amount
    reason: String,
    customer_id: String,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
struct RefundResult {
    refund_id: String,
    status: String,
    amount_refunded: f64,
}

#[task]
async fn process_gateway_refund(charge_id: String, amount: f64) -> Result<String> {
    let refund = gateway::create_refund(&charge_id, amount).await?;
    Ok(refund.id)
}

#[task]
async fn return_inventory(order_id: String) -> Result<()> {
    warehouse::release_reservation(&order_id).await?;
    Ok(())
}

#[task]
async fn update_ledger(order_id: String, refund_id: String, amount: f64) -> Result<()> {
    accounting::record_refund(&order_id, &refund_id, amount).await?;
    Ok(())
}

#[task]
async fn send_refund_notification(customer_id: String, amount: f64) -> Result<()> {
    email::send_refund_confirmation(&customer_id, amount).await?;
    Ok(())
}

#[workflow(name = "process_refund", version = "1.0.0")]
pub async fn process_refund(
    ctx: WorkflowContext,
    request: RefundRequest,
) -> Result<RefundResult> {
    // Step 1: Process refund with payment gateway
    let refund_id = ctx.execute_task(
        process_gateway_refund, (request.charge_id.clone(), request.amount)
    ).await?;

    // Step 2: Return inventory to stock
    ctx.execute_task(return_inventory, request.order_id.clone()).await?;

    // Step 3: Update accounting ledger
    ctx.execute_task(update_ledger, (
        request.order_id.clone(), refund_id.clone(), request.amount
    )).await?;

    // Step 4: Notify customer
    ctx.execute_task(
        send_refund_notification, (request.customer_id.clone(), request.amount)
    ).await?;

    Ok(RefundResult {
        refund_id,
        status: "completed".to_string(),
        amount_refunded: request.amount,
    })
}
```

```typescript
import { Workflow, Tasks, Task, WorkflowContext, createTaskRefs } from '@orcher/sdk';

interface RefundRequest {
  orderId: string;
  chargeId: string;
  amount: number;
  reason: string;
  customerId: string;
}

interface RefundResult {
  refundId: string;
  status: string;
  amountRefunded: number;
}

@Tasks()
class RefundTasks {
  @Task()
  async processGatewayRefund(chargeId: string, amount: number): Promise<string> {
    const refund = await gateway.createRefund(chargeId, amount);
    return refund.id;
  }

  @Task()
  async returnInventory(orderId: string): Promise<void> {
    await warehouse.releaseReservation(orderId);
  }

  @Task()
  async updateLedger(orderId: string, refundId: string, amount: number): Promise<void> {
    await accounting.recordRefund(orderId, refundId, amount);
  }

  @Task()
  async sendRefundNotification(customerId: string, amount: number): Promise<void> {
    await email.sendRefundConfirmation(customerId, amount);
  }
}

const tasks = createTaskRefs(RefundTasks);

@Workflow({ name: 'process_refund', version: '1.0.0' })
class ProcessRefundWorkflow {
  async run(ctx: WorkflowContext, request: RefundRequest): Promise<RefundResult> {
    const refundId = await ctx.executeTask(tasks.processGatewayRefund, request.chargeId, request.amount);
    await ctx.executeTask(tasks.returnInventory, request.orderId);
    await ctx.executeTask(tasks.updateLedger, request.orderId, refundId, request.amount);
    await ctx.executeTask(tasks.sendRefundNotification, request.customerId, request.amount);

    return { refundId, status: 'completed', amountRefunded: request.amount };
  }
}
```

## Design notes

- **Idempotency, same two layers as the charge.** A worker can die inside `process_gateway_refund` after the gateway accepted it — pass an idempotency key derived from the refund request so the retry gets the original refund back instead of issuing a second one. The mechanics are identical to [the charge-side diagram](/guides/use-cases/financial-workflows/payment-processing#two-layers-of-idempotency).
- **Validate partial refunds against what's left.** `amount` supports partial refunds, and one charge may see several. `process_gateway_refund` should check the remaining refundable balance so two support agents processing the same request can't over-refund — the gateway's per-request idempotency key handles duplicates, the balance check handles genuinely distinct requests.
- **Keep the reason in the request.** `request.reason` flows into the workflow's journal and your audit trail — refund analytics and chargeback disputes both want to know *why*, and the field costs nothing.
- **Decide what a failed notification means.** As written, a permanently failing email fails the whole workflow *after* the money and books are already consistent. If that's not what you want, make the last step best-effort — the same policy call as [the confirmation email in payment processing](/guides/use-cases/financial-workflows/payment-processing#how-it-works).
