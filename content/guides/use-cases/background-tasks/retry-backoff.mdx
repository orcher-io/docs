External API calls fail — rate limits, transient errors, network timeouts. Rather than letting a single failure kill your entire workflow, catch the error and retry with exponential backoff using durable timers. The retry loop and backoff delays are all journaled, so if the process crashes between retries, it resumes at the correct attempt count without re-executing successful calls.

## How it works

Each failed attempt doubles the wait before the next one — 1s, 2s, 4s, 8s, 16s — giving a struggling API room to recover instead of hammering it. Every attempt and every backoff sleep is a journaled step, so the attempt counter survives a crash: a restart resumes at the same attempt with the same remaining budget, never resetting the ladder to zero.

use orcher::prelude::*;
use anyhow::Result;
use std::time::Duration;

#[task]
async fn call_external_api(request: ApiRequest) -> Result<ApiResponse> {
    external_api::post(&request.url, &request.body).await
}

#[task]
async fn store_result(result: ApiResponse) -> Result<()> {
    db::insert_api_result(result).await
}

#[task]
async fn send_failure_alert(input: FailureAlert) -> Result<()> {
    alerting::send(input).await
}

#[workflow(name = "resilient_api_call", version = "1.0.0")]
async fn resilient_api_call(
    ctx: WorkflowContext,
    request: ApiRequest,
) -> Result<ApiResponse> {
    let max_retries = 5;

    for attempt in 0..=max_retries {
        match ctx.execute_task(call_external_api, request.clone()).await {
            Ok(response) => {
                ctx.execute_task(store_result, response.clone()).await?;
                return Ok(response);
            }
            Err(e) if attempt < max_retries => {
                // Exponential backoff: 1s, 2s, 4s, 8s, 16s
                let delay = Duration::from_secs(2_u64.pow(attempt));
                ctx.sleep(delay).await?;
            }
            Err(e) => {
                // All retries exhausted — alert and fail
                ctx.execute_task(send_failure_alert, FailureAlert {
                    url: request.url.clone(),
                    attempts: max_retries + 1,
                    last_error: e.to_string(),
                }).await?;
                return Err(e);
            }
        }
    }
    unreachable!()
}

```typescript
import {
  Workflow,
  Tasks,
  Task,
  WorkflowContext,
  createTaskRefs,
} from '@orcher/sdk';

@Tasks()
class ApiTasks {
  @Task()
  async callExternalApi(request: ApiRequest): Promise<ApiResponse> {
    return await externalApi.post(request.url, request.body);
  }

  @Task()
  async storeResult(result: ApiResponse): Promise<void> {
    await db.insertApiResult(result);
  }

  @Task()
  async sendFailureAlert(input: FailureAlert): Promise<void> {
    await alerting.send(input);
  }
}

const tasks = createTaskRefs(ApiTasks);

@Workflow({ name: 'resilient_api_call', version: '1.0.0' })
class ResilientApiCall {
  async run(
    ctx: WorkflowContext,
    request: ApiRequest,
  ): Promise<ApiResponse> {
    const maxRetries = 5;

    for (let attempt = 0; attempt <= maxRetries; attempt++) {
      try {
        const response = await ctx.executeTask(
          tasks.callExternalApi, request,
        );
        await ctx.executeTask(tasks.storeResult, response);
        return response;
      } catch (error) {
        if (attempt < maxRetries) {
          // Exponential backoff: 1s, 2s, 4s, 8s, 16s
          const delay = Math.pow(2, attempt) * 1000;
          await ctx.sleep(delay);
        } else {
          // All retries exhausted — alert and fail
          await ctx.executeTask(tasks.sendFailureAlert, {
            url: request.url,
            attempts: maxRetries + 1,
            lastError: String(error),
          });
          throw error;
        }
      }
    }

    throw new Error('Unreachable');
  }
}
```

Each retry attempt is a separate journaled task execution. If attempt 3 succeeds, the result is cached — on replay, Orcher returns the cached response without hitting the external API again. The exponential backoff delays use durable timers, so they're also replay-safe.

## Don't reach for this too soon

Orcher already retries a failing task automatically before the error ever reaches your workflow code. The manual loop on this page is for the cases the automatic policy can't express — reach for it deliberately, not by default.

## Design notes

- **Add jitter to the delay.** Pure `2^n` backoff means every workflow that failed at the same moment retries at the same moment — a thundering herd that re-overloads the API you're backing off from. Add a random fraction to each delay so retries spread out. (Randomness must come from a task, not inline in the workflow — see the [determinism rules](/guides/core/workflows/determinism).)
- **Retry only what retrying can fix.** A `429` or `503` is worth waiting on; a `400` or `401` will fail identically every attempt. Inspect the error and fail fast on permanent ones instead of burning the whole ladder — 31 seconds spent re-sending a malformed request is 31 seconds wasted.
- **Cap total time, not just attempt count.** Five attempts with doubling delays is ~31s of backoff; raising the ceiling to 10 attempts is ~17 *minutes*. If a caller is waiting on this workflow, bound the wall-clock budget explicitly rather than reasoning about it from the exponent.
- **Retries assume idempotency.** A retried `POST` that already succeeded server-side (but whose response was lost) double-submits. Where the call isn't naturally idempotent, send an idempotency key — the same defense as [payment processing](/guides/use-cases/financial-workflows/payment-processing#two-layers-of-idempotency).
