The most common event-driven pattern is reacting to domain events and triggering side effects. When an order is created, reserve inventory. When payment is received, create a shipment. When an order is cancelled, release the reservation. Each event handler is a workflow that executes tasks durably — if the worker crashes after reserving inventory but before emitting the confirmation event, replay picks up from the last checkpoint.

## How it works

One workflow, `handle_order_event`, is the dispatcher: it matches on the event type and runs the matching reaction chain. Each incoming event starts its own execution of this workflow, so a thousand orders a minute is a thousand independent, individually-journaled runs.

```rust
use orcher::prelude::*;
use anyhow::Result;

#[task]
async fn reserve_inventory(items: Vec<OrderItem>) -> Result<ReservationId> {
    inventory_client::reserve(items).await
}

#[task]
async fn create_shipment(order_id: String) -> Result<TrackingNumber> {
    shipping_client::create_shipment(&order_id).await
}

#[task]
async fn release_inventory(order_id: String) -> Result<()> {
    inventory_client::release(&order_id).await
}

#[task]
async fn send_notification(input: NotificationInput) -> Result<()> {
    notification_client::send(input).await
}

#[workflow(name = "handle_order_event", version = "1.0.0")]
async fn handle_order_event(
    ctx: WorkflowContext,
    event: OrderEvent,
) -> Result<()> {
    match event.event_type.as_str() {
        "order.created" => {
            let reservation = ctx.execute_task(
                reserve_inventory, event.items.unwrap(),
            ).await?;
            ctx.execute_task(send_notification, NotificationInput {
                user_id: event.user_id,
                message: format!("Order {} confirmed, reservation {}", event.order_id, reservation),
            }).await?;
        }
        "payment.received" => {
            let tracking = ctx.execute_task(
                create_shipment, event.order_id.clone(),
            ).await?;
            ctx.execute_task(send_notification, NotificationInput {
                user_id: event.user_id,
                message: format!("Order {} shipped, tracking {}", event.order_id, tracking),
            }).await?;
        }
        "order.cancelled" => {
            ctx.execute_task(release_inventory, event.order_id.clone()).await?;
            ctx.execute_task(send_notification, NotificationInput {
                user_id: event.user_id,
                message: format!("Order {} cancelled", event.order_id),
            }).await?;
        }
        _ => {} // Ignore unknown events
    }
    Ok(())
}
```

```typescript
import {
  Workflow,
  Tasks,
  Task,
  WorkflowContext,
  createTaskRefs,
} from '@orcher/sdk';

@Tasks()
class OrderEventTasks {
  @Task()
  async reserveInventory(items: OrderItem[]): Promise<string> {
    return await inventoryClient.reserve(items);
  }

  @Task()
  async createShipment(orderId: string): Promise<string> {
    return await shippingClient.createShipment(orderId);
  }

  @Task()
  async releaseInventory(orderId: string): Promise<void> {
    await inventoryClient.release(orderId);
  }

  @Task()
  async sendNotification(input: NotificationInput): Promise<void> {
    await notificationClient.send(input);
  }
}

const tasks = createTaskRefs(OrderEventTasks);

@Workflow({ name: 'handle_order_event', version: '1.0.0' })
class HandleOrderEvent {
  async run(ctx: WorkflowContext, event: OrderEvent): Promise<void> {
    switch (event.eventType) {
      case 'order.created': {
        const reservation = await ctx.executeTask(
          tasks.reserveInventory, event.items!,
        );
        await ctx.executeTask(tasks.sendNotification, {
          userId: event.userId,
          message: `Order ${event.orderId} confirmed, reservation ${reservation}`,
        });
        break;
      }
      case 'payment.received': {
        const tracking = await ctx.executeTask(
          tasks.createShipment, event.orderId,
        );
        await ctx.executeTask(tasks.sendNotification, {
          userId: event.userId,
          message: `Order ${event.orderId} shipped, tracking ${tracking}`,
        });
        break;
      }
      case 'order.cancelled': {
        await ctx.executeTask(tasks.releaseInventory, event.orderId);
        await ctx.executeTask(tasks.sendNotification, {
          userId: event.userId,
          message: `Order ${event.orderId} cancelled`,
        });
        break;
      }
    }
  }
}
```

Each event triggers a new workflow execution. If your service processes 1,000 `order.created` events per minute, that's 1,000 independent workflow executions — each with its own journal, its own retry logic, and its own crash recovery. You can trigger these workflows from any external source (webhook endpoint, message queue consumer, or the CLI).

## The two guarantees an event bus won't give you

Durable execution makes each *reaction* reliable, but the *delivery* still comes from your event source — and real event buses are at-least-once and unordered. Both leak into this handler:

When ordering actually matters, don't try to sort events in the dispatcher — route them to a per-entity [actor](/guides/use-cases/event-driven/stateful-actors), whose single-writer guarantee applies each event against the entity's current state regardless of arrival order.

## Design notes

- **Make each reaction idempotent.** Derive downstream keys from the event (order ID, a dedupe key on the event itself) so a redelivered event is a no-op — the same defense as [payment processing](/guides/use-cases/financial-workflows/payment-processing#two-layers-of-idempotency).
- **The `_` arm is a feature.** Ignoring unknown event types lets producers add new events before this consumer learns to handle them — forward compatibility for free. Log the ignored type so a genuinely-missed handler is visible.
- **One handler per event keeps failures isolated.** A poison event that always fails retries and parks *its own* execution; the other 999 orders that minute are untouched. Contrast a single loop consuming a partition, where one bad message can stall everything behind it.
- **The dispatcher grows into child workflows.** As each arm gains steps, a fat `match` becomes hard to read and test. Give each event type its own [child workflow](/guides/use-cases/distributed-systems/child-workflows#child-workflow-or-plain-task) and let the dispatcher just route.
