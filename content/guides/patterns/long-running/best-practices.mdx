## Best Practices

### 1. Use Durable Timers, Not Polling

Durable timers are Orcher's most resource-efficient primitive. A sleeping workflow consumes zero CPU and minimal storage — just a single database row. Never implement delays by polling in a tight loop, which wastes resources and creates unnecessary load on your task infrastructure.

```rust
// Good - Durable timer: zero resource consumption while waiting
ctx.sleep(Duration::from_secs(3600)).await?;
ctx.execute_task(check_status, id.clone()).await?;

// Bad - Polling wastes resources and creates unnecessary task executions
loop {
    let status: Status = ctx.execute_task(check_status, id.clone()).await?;
    if status.is_ready() {
        break;
    }
    // Still running during sleep - wastes resources!
    tokio::time::sleep(Duration::from_secs(10)).await;
}
```

### 2. Set Reasonable Timeouts

Every human interaction or external event wait should have a timeout. Without one, a workflow can block indefinitely if the expected signal never arrives. Choose timeouts that match your business SLA — 48 hours for an approval, 30 minutes for a payment, 7 days for document upload — and always handle the timeout case with an escalation path or default action.

```rust
// Good - Timeout prevents infinite wait
let approval: Option<ApprovalDecision> = ctx
    .wait_for_event_with_timeout("approval", Duration::from_secs(172800))
    .await?;

match approval {
    Some(decision) => handle_approval(decision),
    None => escalate_or_reject(),
}

// Bad - No timeout, could wait forever
let approval: ApprovalDecision = ctx.wait_for_event("approval").await?;
```

### 3. Track Progress with Checkpoints

For workflows that span hours or days, recording progress at key milestones gives you observability into where each workflow stands. This is invaluable for debugging, customer support, and operational dashboards. Store checkpoints as workflow state so they're queryable from outside the workflow.

```rust
// Good - Track progress at each milestone
let mut state = ProcessState::new();

state.checkpoints.push("started");
ctx.set_state("process_state", &state).await?;

// ... do work ...

state.checkpoints.push("halfway_complete");
ctx.set_state("process_state", &state).await?;
```

### 4. Handle Long Wait Failures

When a long-running wait times out, don't just fail the workflow. Build graceful degradation into your timeout handling: send a reminder, extend the deadline, escalate to a manager, or fall back to a default action. This keeps the business process moving even when humans are slow to respond.

```rust
// Good - Graceful handling with reminder and extended deadline
let payment: Option<Payment> = ctx
    .wait_for_event_with_timeout("payment", Duration::from_secs(1800))
    .await?;

match payment {
    Some(payment) => process_payment(payment).await?,
    None => {
        // Timeout - send reminder and extend deadline
        ctx.execute_task(send_payment_reminder, user_id.clone()).await?;

        let extended_payment: Option<Payment> = ctx
            .wait_for_event_with_timeout("payment", Duration::from_secs(3600))
            .await?;

        match extended_payment {
            Some(p) => process_payment(p).await?,
            None => cancel_order().await?,
        }
    }
}
```

### 5. Use Appropriate Time Scales

When writing sleep durations, prefer named constants or comments that make the intended duration immediately obvious. Raw numbers like `1209600` are hard to review and easy to get wrong. Rust's `Duration::from_secs` with clear comments is far more maintainable than `Duration::from_millis` with large numbers.

```rust
// Good - Clear, readable durations
ctx.sleep(Duration::from_secs(3600)).await?;     // 1 hour
ctx.sleep(Duration::from_secs(86400)).await?;    // 1 day
ctx.sleep(Duration::from_secs(604800)).await?;   // 1 week

// Bad - Confusing large numbers without context
ctx.sleep(Duration::from_millis(3600000)).await?;  // What is this?
ctx.sleep(Duration::from_secs(1209600)).await?;    // Hard to read
```

### 6. Consider Time Zones

When your workflow needs to execute at a specific wall-clock time (e.g., "send at 9 AM Eastern"), you must compute the sleep duration relative to the target time in the correct timezone. Simply sleeping for a fixed number of hours won't account for DST transitions or timezone offsets.

```rust
// Good - Explicit timezone handling
use chrono::{DateTime, Utc, TimeZone};
use chrono_tz::America::New_York;

// Schedule for 9 AM Eastern Time
let target_time = New_York
    .ymd(2024, 1, 15)
    .and_hms(9, 0, 0)
    .with_timezone(&Utc);

let now = Utc::now();
let wait_duration = (target_time - now).to_std()?;

ctx.sleep(wait_duration).await?;
```

## Performance Considerations

### Timer Storage

Each durable timer creates a single database entry with minimal overhead (less than 1KB). Timers are indexed for efficient firing and consume no CPU or memory while waiting. As a rule of thumb, timers are very cheap — use them freely for any delay, whether it's 5 minutes or 5 weeks.

### Concurrent Long-Running Workflows

Orcher efficiently handles large numbers of concurrent long-running workflows because sleeping workflows consume almost no resources. The primary constraint is database storage for timer entries and journal rows.

| Concurrent Workflows | Memory Usage | Database Load |
|----------------------|--------------|---------------|
| 1,000 | Minimal | Low |
| 10,000 | Low | Low |
| 100,000 | Moderate | Moderate |
| 1,000,000+ | Carefully tune | Carefully tune |

### Wake-Up Latency

Timer wake-up latency depends on the timer duration and the polling interval of Orcher's internal timer subsystem. For most use cases, the latency is negligible relative to the timer duration itself.

| Timer Duration | Wake-Up Latency | Use Case |
|----------------|-----------------|----------|
| < 1 minute | ±1 second | Short delays |
| 1-60 minutes | ±5 seconds | Moderate delays |
| 1-24 hours | ±30 seconds | Daily tasks |
| > 24 hours | ±2 minutes | Long-term processes |

## Common Patterns Summary

This table summarizes the most common long-running process patterns and their typical durations to help you choose the right approach for your use case.

| Pattern | Duration | Use Case | Example |
|---------|----------|----------|---------|
| **Short Delay** | Minutes | Rate limiting, retries | Wait 5 minutes, retry |
| **Human Approval** | Hours to Days | Reviews, decisions | Wait 48 hours for approval |
| **Trial Period** | Days to Weeks | Free trials, subscriptions | 14-day trial period |
| **Order Fulfillment** | Days | Multi-stage processes | 3-7 day delivery |
| **Recurring Task** | Hours to Days | Scheduled reports, cleanup | Daily at midnight |
| **Reminder Series** | Days to Weeks | User engagement | Day 1, 3, 7 reminders |
| **Timeout Pattern** | Minutes to Hours | External system waits | 30-minute payment timeout |
