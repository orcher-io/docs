## Best Practices

### 1. Control Concurrency

Always limit the number of parallel operations to avoid overwhelming downstream systems, exhausting database connections, or running out of memory. Start with a conservative limit (e.g., 50) and tune based on monitoring.

```rust
// Good - Controlled concurrency
const MAX_CONCURRENT: usize = 50;

for chunk in items.chunks(MAX_CONCURRENT) {
    let tasks: Vec<_> = chunk
        .iter()
        .map(|item| ctx.execute_task(process_item, item.clone()))
        .collect();

    for task in tasks {
        results.push(task.await?);
    }
}

// Bad - Unbounded parallelism (could be 10,000+ items!)
let tasks: Vec<_> = items
    .iter()
    .map(|item| ctx.execute_task(process_item, item.clone()))
    .collect();
```

### 2. Handle Partial Failures

Don't let one failed item abort the entire batch. Catch errors per-item and collect both successes and failures, giving the caller enough information to retry just the failed items or accept the partial result.

```rust
// Good - Continue on partial failures
for (item_id, task) in task_handles {
    match task.await {
        Ok(result) => successful.push(result),
        Err(e) => {
            eprintln!("Task failed: {}", e);
            failed.push((item_id, e));
        }
    }
}

// Bad - One failure stops everything
for task in task_handles {
    let result = task.await?;  // Aborts at first error
    results.push(result);
}
```

### 3. Aggregate Results Efficiently

For large result sets, avoid collecting all results into memory before aggregating. Instead, compute running aggregates (sum, count, min, max) as results arrive. This keeps memory usage constant regardless of how many items you process.

```rust
// Good - Stream aggregation (constant memory)
let mut total = 0;
for task in tasks {
    let value = task.await?;
    total += value;
}

// Bad - Collect all then aggregate (memory proportional to item count)
let results: Vec<_> = /* collect all results */;
let total: i32 = results.iter().sum();
```

### 4. Set Appropriate Timeouts

Each fanned-out task should have a timeout that matches its expected duration. Without timeouts, a single hung task can block the entire fan-in phase indefinitely.

```rust
// Good - Task-appropriate timeout
#[task(name = "api_call", timeout_mins = 1)]    // API calls: 1 minute
#[task(name = "batch_import", timeout_mins = 30)] // Imports: 30 minutes

// Bad - Timeout too short for the operation
#[task(name = "long_computation", timeout_mins = 1)]  // Actually takes hours!
```

### 5. Monitor Progress

For long-running fan-out operations, log progress at regular intervals so operators can see how much work remains and estimate completion time.

```rust
// Good - Progress tracking
let total = items.len();
let mut completed = 0;

for task in tasks {
    task.await?;
    completed += 1;
    if completed % 100 == 0 || completed == total {
        println!("Progress: {}/{} ({:.1}%)",
            completed, total, (completed as f64 / total as f64) * 100.0);
    }
}
```

### 6. Choose Tasks vs Child Workflows

Use tasks for lightweight, fast operations (under a few seconds) and child workflows for complex, multi-step operations that need independent error handling, their own journal, or may take minutes to complete.

```rust
// Good - Tasks for simple, fast operations
for item in items {
    ctx.execute_task(validate_item, item).await?;  // Milliseconds
}

// Good - Child workflows for complex operations
for order in orders {
    ctx.start_child_workflow("process_order", order).await?;  // Minutes, multi-step
}

// Bad - Child workflows for trivial operations (unnecessary overhead)
for item in items {
    ctx.start_child_workflow("validate_item", item).await?;  // Overkill
}
```

## Performance Considerations

### Parallelism Limits

The degree of parallelism directly impacts resource usage. Choose a concurrency level appropriate for your workload and downstream system capacity.

| Concurrent Operations | Memory Usage | Network Connections | Recommended For |
|-----------------------|--------------|---------------------|-----------------|
| 1-10 | Minimal | Low | Small batches |
| 10-50 | Low | Moderate | Standard processing |
| 50-100 | Moderate | High | High throughput |
| 100+ | High | Very High | Carefully tune |

**Rule of thumb:** Start with 50 concurrent operations and tune based on monitoring.

### Latency Analysis

Fan-out/fan-in latency is determined by three components: the time to dispatch all tasks (fan-out overhead), the time for the slowest task to complete (parallel execution), and the time to collect results (fan-in overhead).

### Result Collection Strategies

Choose a collection strategy based on the number of results and available memory.

```rust
// Strategy 1: Collect all (good for < 10K results)
let results: Vec<_> = /* await all tasks */;

// Strategy 2: Stream aggregation (good for any size, constant memory)
let mut aggregate = Aggregate::new();
for task in tasks {
    let result = task.await?;
    aggregate.add(result);
}

// Strategy 3: Batch collection (good for > 10K results)
for chunk in task_handles.chunks(1000) {
    let batch_results = /* await chunk */;
    persist_batch(batch_results).await?;
}
```

## Common Patterns Summary

| Pattern | Use Case | Example |
|---------|----------|---------|
| **Basic Fan-Out/Fan-In** | Independent operations | Parallel API calls |
| **Rate-Limited Fan-Out** | Protect downstream systems | API with rate limits |
| **Partial Failure Handling** | Resilient processing | Optional validations |
| **Dynamic Fan-Out** | Variable workload | Multi-source aggregation |
| **Nested Fan-Out** | Hierarchical processing | Region → Store → Product |
| **Streaming Fan-In** | Large result sets | Big data aggregation |
