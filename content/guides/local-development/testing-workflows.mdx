There are two kinds of test for a workflow, and they answer different questions.

| Test | Runs | Tells you | Needs |
|---|---|---|---|
| In memory | The workflow function alone. Tasks are mocks and timers do not wait. | The workflow's logic is right: which tasks it calls, in what order, with what result. | Nothing but the SDK |
| On the engine | The real worker, the real tasks and the real engine. | The project works as deployed: the workflow and tasks are registered, inputs and results serialize, timers fire. | A running engine |

The examples test the `welcome` workflow from [Workflow development](/guides/local-development/workflow-development), in a project made with `orcher new`.

## The check that comes with the project

A generated project already has one test on the engine, for its `hello` workflow. With the engine running, in the project directory:

```bash
orcher test
```

It builds the project, runs that test, and ends with:

```
✓  The project's workflows ran end to end
```

`orcher test --dry-run` only checks that the project builds, and needs no engine.

## Test in memory

Each SDK has a test environment that runs a workflow without an engine or a worker. You name the tasks the workflow calls and say what each returns.

The ten-second timer in `welcome` does not make these tests slow: the test environment does not wait for it.

## Test on the engine

This test starts a worker inside the test process, starts the workflow through a client, and checks the result. Nothing is mocked. It uses the project's own settings and worker, so it runs against whatever engine the project points at: `http://localhost:50051` unless `ORCHER_SERVER` says otherwise.

This test takes ten seconds, because the timer is real, and it fails with a connection error when no engine is running. Keep tests like it few, and put the detailed cases in memory.

Stop any worker you have running on the same task queue first. Otherwise that worker may pick up the test's workflow and run it with whatever code it loaded.

## An engine for tests in CI

A CI job needs the same thing your machine has: Postgres and the engine. Any runner with Docker can start both and wait until the engine is ready:

```bash
docker network create orcher
docker run -d --name orcher-postgres --network orcher \
  -e POSTGRES_USER=orcher -e POSTGRES_PASSWORD=orcher -e POSTGRES_DB=orcher \
  postgres:17-alpine
docker run -d --name orcher --network orcher \
  -p 127.0.0.1:50051:50051 -p 127.0.0.1:8080:8080 \
  -e DATABASE_URL=postgresql://orcher:orcher@orcher-postgres:5432/orcher \
  -e ORCHER_INSECURE=true \
  ghcr.io/orcher-io/orcher:0.7.5
until curl -fsS localhost:8080/health/ready >/dev/null 2>&1; do sleep 1; done; echo ready
```

Then run the tests as above. `ORCHER_INSECURE=true` is what lets the engine serve without authentication from inside a container; without it and without authentication configured, the engine exits with an error that says so.
