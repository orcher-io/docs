On your machine there are three things to configure, and each has its own place:

- **Your worker and clients** take the engine's address, a namespace and a task queue in code.
- **The CLI** takes the engine's address and a namespace from flags, environment variables or a saved context.
- **The engine** is configured with environment variables on its container, and optionally a TOML file.

With the defaults nothing needs setting: the engine listens on `localhost:50051`, and the CLI and a project made with `orcher new` both look there, in the `default` namespace.

| Variable | Default | Meaning |
|---|---|---|
| `ORCHER_SERVER` | `http://localhost:50051` | The engine's gRPC address |
| `ORCHER_NAMESPACE` | `default` | The namespace the worker polls and workflows start in |
| `ORCHER_API_KEY` | unset | A key for an engine that requires one. A local engine does not. |
| `ORCHER_TASK_QUEUE` | `welcome` | The task queue. The generated project fixes this to the project's name; the line above is an addition. |

These names are the project's choice, read by the code above, and not something the SDKs look up on their own. The one exception is the Python SDK, whose client and worker builder read `ORCHER_API_KEY` themselves when no key is passed.

### Share one engine

Workers that poll the same task queue in the same namespace share its work, whoever started them. Two people on one engine, or two checkouts on one machine, will run each other's workflows unless they use different queues or namespaces.

A different task queue needs nothing set up. Start the worker and the workflow with the same name:

```bash
export ORCHER_TASK_QUEUE=welcome-ada
```

A namespace has to exist before a worker can poll it. Until it does, the worker logs `Namespace 'dev' does not exist or is not active` and keeps retrying. Create it once:

```bash
orcher namespace create dev
export ORCHER_NAMESPACE=dev
```

`orcher workflow list` then shows only that namespace's workflows, because the CLI reads `ORCHER_NAMESPACE` too. `orcher workflow list -A` lists every namespace.

## The CLI

Every command takes these, as a flag or from the environment:

| Flag | Environment | Default | Meaning |
|---|---|---|---|
| `--server` | `ORCHER_SERVER` | the current context's, else `http://localhost:50051` | The engine's gRPC address |
| `--api-url` | `ORCHER_API_URL` | the `--server` host on port 8080 | The engine's HTTP address, for the commands that use the REST API |
| `-n`, `--namespace` | `ORCHER_NAMESPACE` | `default` | The namespace to act in |
| | `ORCHER_API_KEY` | none | A key for an engine that requires one |
| `--context` | `ORCHER_CONTEXT` | the current context | A saved engine address and namespace |
| `--config` | `ORCHER_CONFIG` | `~/.orcher/config.yaml` | The CLI's own config file, where contexts are kept |

To keep an address instead of exporting it in every terminal, save it as a context and switch to it. This one is for a local engine started on other ports, in the `dev` namespace:

```bash
orcher config set-context alt --server http://localhost:50061 --namespace dev
orcher config use-context alt
orcher config get-contexts          # the current one is marked with *
orcher config test-connection       # checks that the engine answers
```

`orcher config use-context local` switches back to the local engine. The `local` context exists from the start.

## The local engine

### Started with the CLI

`orcher dev start` takes the settings that matter day to day:

| Flag | Default | Meaning |
|---|---|---|
| `--engine-version` | `0.6.2` in CLI 0.1.4 | The engine release to run. Use `0.7.2`. |
| `--port` | `50051` | Host port for gRPC |
| `--http-port` | `8080` | Host port for HTTP |
| `--no-ui` | off | Start the engine without its dashboard |
| `--open` | off | Open the dashboard in a browser once the engine is ready |

`orcher server start` starts the same engine and adds `--log-level` (`trace`, `debug`, `info`, `warn` or `error`), `--engine-config` for a TOML file, and `--database-url` to use a PostgreSQL database you already run instead of starting one. On that command the gRPC port flag is `--grpc-port`, and `--database-url` is also read from a `DATABASE_URL` variable in your shell, so unset that first if you want the CLI to start Postgres itself.

### Started with Docker

The engine reads environment variables. These are the ones that matter locally:

| Variable | Default in the image | Meaning |
|---|---|---|
| `DATABASE_URL` | none; required | The PostgreSQL 14+ database. It must exist; the engine creates its tables in it on start. |
| `ORCHER_INSECURE` | unset | `true` lets the engine serve without authentication from inside a container. Without it, and without authentication configured, the engine exits at start with an error that says so. |
| `GRPC_BIND_ADDR` | `0.0.0.0:50051` | Where the gRPC API listens inside the container |
| `HTTP_BIND_ADDR` | `0.0.0.0:8080` | Where the dashboard, the REST API, `/health/ready` and `/metrics` listen |
| `LOG_LEVEL` | `info` | `trace`, `debug`, `info`, `warn` or `error` |
| `LOG_FORMAT` | `compact` | `compact`, `pretty` or `json` |
| `ORCHER_UI_ENABLED` | `true` | `false` serves the API without the dashboard |
| `ORCHER_ORCHESTRATOR_CONFIG` | unset | Path, inside the container, of a TOML config file |

The engine image's [README](https://github.com/orcher-io/orcher/blob/main/docker/engine/README.md) lists the rest.

The Compose file in the [quickstart repository](https://github.com/orcher-io/quickstart) sets these for you and reads four variables of its own:

| Variable | Default | Meaning |
|---|---|---|
| `ORCHER_IMAGE` | `ghcr.io/orcher-io/orcher:0.7.2` | The engine image |
| `ORCHER_GRPC_PORT` | `50051` | Host port for gRPC |
| `ORCHER_HTTP_PORT` | `8080` | Host port for HTTP |
| `ORCHER_LOG_LEVEL` | `info` | The engine's `LOG_LEVEL` |

```bash
ORCHER_GRPC_PORT=50061 ORCHER_HTTP_PORT=8081 docker compose up -d --wait
export ORCHER_SERVER=http://localhost:50061
export ORCHER_API_URL=http://localhost:8081
```

The engine needs no other service. Postgres is the only thing it depends on.

## Try authentication locally

A local engine has authentication off. To see how your code behaves against an engine that requires an API key, start one with a config file that turns it on.

The file has to be complete: the engine rejects a file that holds only a `[security]` section. Start from the example in the engine repository and add the section to it:

```bash
curl -fsSL -o engine.toml https://raw.githubusercontent.com/orcher-io/orcher/v0.7.2/services/orchestrator/config.example.toml
printf '\n[security]\nauth_mode = "api-key"\n' >> engine.toml
```

Stop the engine you have running, then start one with the file:

```bash
orcher dev stop
orcher server start --engine-version 0.7.2 --engine-config engine.toml
```

Every call now needs a key. `orcher workflow list` fails with `Missing authorization header`. Issue the first key from inside the engine's container. It is printed once:

```bash
docker exec orcher-dev-engine orchestrator api-key create --name local --scope '*'
```

Export it, and the CLI and the project above both use it:

```bash
export ORCHER_API_KEY=<the key>
orcher workflow list
```

To go back, run `orcher server stop`, then `orcher dev start --engine-version 0.7.2`, and `unset ORCHER_API_KEY`.
