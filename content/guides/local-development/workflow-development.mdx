## What is a Workflow?

A **workflow** is a durable function that orchestrates multiple steps (tasks) with automatic journaling. If a workflow crashes, it resumes exactly where it left off without re-executing completed steps.

**Key characteristics:**

• **Durable** - Survives crashes and restarts
• **Deterministic** - Same inputs produce same outputs
• **Journaled** - Every step is automatically recorded
• **Typed** - Full compile-time type safety
• **Composable** - Can call other workflows as children

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="sdk"
>

<TabPanel id="rust" label="Rust">

```rust
use orcher::prelude::*;

#[workflow(
    name = "payment_workflow",
    version = "1.0.0",
    description = "Process payment with durable execution"
)]
async fn payment_workflow(
    ctx: WorkflowContext,
    input: PaymentInput,
) -> orcher::Result<PaymentOutput> {
    // Step 1: Charge card (automatically journaled)
    let charge: ChargeResult = ctx
        .execute_task("charge_card", (input.amount, input.card_token.clone()))
        .await?;
    
    // Step 2: Reserve inventory (automatically journaled)
    let inventory: InventoryResult = ctx
        .execute_task("reserve_inventory", input.order_id.clone())
        .await?;
    
    // Step 3: Send confirmation (automatically journaled)
    let notification: NotificationResult = ctx
        .execute_task(
            "send_confirmation_email",
            (input.customer_email.clone(), charge.charge_id.clone()),
        )
        .await?;
    
    Ok(PaymentOutput::new(
        input.order_id,
        charge.charge_id,
        inventory.reserved,
        notification.sent,
        "completed".to_string(),
    ))
}
```

## Creating Your First Workflow

### 1. Define the Workflow

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"

>

<TabPanel id="rust" label="Rust">

Create a workflow using the `#[workflow]` attribute macro:

```rust
use orcher::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
pub struct GreetingInput {
    pub name: String,
}

#[derive(Debug, Serialize, Deserialize)]
pub struct GreetingOutput {
    pub message: String,
}

#[workflow(
    name = "greet_workflow",
    version = "1.0.0",
    description = "Simple greeting workflow"
)]
async fn greet_workflow(
    ctx: WorkflowContext,
    input: GreetingInput,
) -> orcher::Result<GreetingOutput> {
    let message = format!("Hello, {}!", input.name);
    
    Ok(GreetingOutput { message })
}
```

**Workflow Attributes:**

• `name` - Unique workflow identifier (defaults to function name)
• `version` - Semantic version for tracking changes
• `description` - Human-readable description for docs
• `namespace` - Optional namespace for organization
• `timeout` - Maximum execution time (e.g., `timeout = "1h"`)

## Workflow Context API

The `WorkflowContext` provides methods for durable operations. All operations through the context are automatically journaled.

### Execute Tasks

Orcher provides two ways to execute durable steps that are automatically journaled and replay-protected:

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="sdk"
>

<TabPanel id="rust" label="Rust">

#### Method 1: `ctx.execute()` - Inline Closures

Use for one-off operations specific to a single workflow:

```rust
#[workflow]
async fn order_workflow(ctx: WorkflowContext, order: Order) -> orcher::Result<Receipt> {
    // Inline closure - code lives in the workflow
    let payment = ctx
        .execute("charge_card", || async move {
            // One-off logic here
            let client = StripeClient::new();
            client.charge(order.amount, order.card_token.clone()).await
        })
        .await?;
    
    // Another inline operation
    let inventory = ctx
        .execute("reserve_inventory", || async move {
            let db = Database::connect().await?;
            db.reserve_items(order.items.clone()).await
        })
        .await?;
    
    Ok(Receipt { payment, inventory })
}
```

**Advantages:**
• Quick to write - no separate task definition needed
• Good for workflow-specific logic
• Keeps related code together
• Perfect for prototyping

**When to use:**
• One-off operations not reused elsewhere
• Workflow-specific business logic
• Simple external API calls
• Rapid prototyping

#### Method 2: `ctx.execute_task()` - Registered Tasks

Use for reusable operations shared across workflows:

```rust
// Define task once (in tasks/ module)
#[task(
    name = "charge_card",
    description = "Charge credit card via Stripe",
    retry = 3
)]
async fn charge_card(ctx: TaskContext, input: (f64, String)) -> Result<ChargeResult> {
    let (amount, card_token) = input;
    let client = StripeClient::new();
    client.charge(amount, card_token).await
}

// Use in multiple workflows
#[workflow]
async fn order_workflow(ctx: WorkflowContext, order: Order) -> orcher::Result<Receipt> {
    // Call registered task by name
    let payment = ctx
        .execute_task("charge_card", (order.amount, order.card_token.clone()))
        .await?;
    
    // Another registered task
    let inventory = ctx
        .execute_task("reserve_inventory", order.items.clone())
        .await?;
    
    Ok(Receipt { payment, inventory })
}

#[workflow]
async fn subscription_workflow(ctx: WorkflowContext, sub: Subscription) -> orcher::Result<()> {
    // Same task, different workflow!
    let payment = ctx
        .execute_task("charge_card", (sub.amount, sub.card_token.clone()))
        .await?;
    
    Ok(())
}
```

**Advantages:**
• Reusable across multiple workflows
• Centralized retry and timeout configuration
• Easier to test in isolation
• Better separation of concerns
• Can be versioned independently

**When to use:**
• Shared operations across workflows
• Complex logic that needs testing
• Operations with specific retry policies
• Third-party integrations
• Team-shared functionality

#### Comparison Example

```rust
// Inline - repeated code
#[workflow]
async fn workflow_a(ctx: WorkflowContext, input: Input) -> orcher::Result<Output> {
    let email = ctx.execute("send_email", || async move {
        EmailClient::new().send(input.to, input.subject, input.body).await
    }).await?;
    Ok(Output { email })
}

#[workflow]
async fn workflow_b(ctx: WorkflowContext, input: Input) -> orcher::Result<Output> {
    // Same code duplicated!
    let email = ctx.execute("send_email", || async move {
        EmailClient::new().send(input.to, input.subject, input.body).await
    }).await?;
    Ok(Output { email })
}

// Registered task - reused
#[task(name = "send_email", retry = 3)]
async fn send_email(ctx: TaskContext, input: EmailRequest) -> Result<EmailResult> {
    EmailClient::new().send(input.to, input.subject, input.body).await
}

#[workflow]
async fn workflow_a(ctx: WorkflowContext, input: Input) -> orcher::Result<Output> {
    let email = ctx.execute_task("send_email", input.email_request).await?;
    Ok(Output { email })
}

#[workflow]
async fn workflow_b(ctx: WorkflowContext, input: Input) -> orcher::Result<Output> {
    let email = ctx.execute_task("send_email", input.email_request).await?;
    Ok(Output { email })
}
```

#### Mixing Both Approaches

You can freely mix both approaches in the same workflow:

```rust
#[workflow]
async fn hybrid_workflow(ctx: WorkflowContext, order: Order) -> orcher::Result<Receipt> {
    // Use registered task for common operations
    let payment = ctx
        .execute_task("charge_card", (order.amount, order.card_token))
        .await?;
    
    // Use inline for one-off logic
    let fraud_check = ctx
        .execute("check_fraud_score", || async move {
            // Custom logic specific to this workflow
            let score = fraud_service::analyze(order.clone()).await?;
            if score > 0.8 {
                return Err(anyhow::anyhow!("High fraud risk"));
            }
            Ok(score)
        })
        .await?;
    
    // Use registered task again
    let inventory = ctx
        .execute_task("reserve_inventory", order.items)
        .await?;
    
    Ok(Receipt { payment, fraud_check, inventory })
}
```

### Event Gates

Wait for external events (human-in-the-loop, external system notifications):

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="sdk"
>

<TabPanel id="rust" label="Rust">

```rust
#[workflow]
async fn approval_workflow(
    ctx: WorkflowContext,
    request: ApprovalRequest,
) -> orcher::Result<ApprovalResult> {
    // Request approval
    ctx.execute_task("notify_manager", request.manager_email.clone()).await?;
    
    // Wait for the approval event with a 24h deadline.
    // Returns Ok(None) if no event arrives before the timeout.
    let approval = ctx
        .wait_for_event_with_timeout::<Approval>("manager_approval", Duration::from_secs(86400))
        .await?;
    
    // Process approval if it arrived before the deadline
    match approval {
        Some(approval) if approval.approved => {
            ctx.execute_task("process_request", request.clone()).await?;
            Ok(ApprovalResult { approved: true })
        }
        _ => Ok(ApprovalResult { approved: false }),
    }
}
```

**Sending events from the client:**

```rust
// From another service or UI — events are delivered through a workflow handle
let handle = client.get_workflow_handle(workflow_id).await?;
handle.send_event("manager_approval", Approval {
    approved: true,
    comment: "Looks good!".to_string(),
}).await?;
```

### Child Workflows

Compose workflows by calling other workflows:

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="sdk"
>

<TabPanel id="rust" label="Rust">

```rust
#[workflow]
async fn parent_workflow(
    ctx: WorkflowContext,
    order: Order,
) -> orcher::Result<OrderResult> {
    // Execute child workflows in parallel
    let (payment, inventory, shipping) = tokio::join!(
        ctx.execute_child_workflow("payment_workflow", order.payment_info.clone()),
        ctx.execute_child_workflow("inventory_workflow", order.items.clone()),
        ctx.execute_child_workflow("shipping_workflow", order.address.clone()),
    );
    
    Ok(OrderResult {
        payment: payment?,
        inventory: inventory?,
        shipping: shipping?,
    })
}
```

**Benefits:**

• Isolate concerns (each workflow handles one domain)
• Reuse workflows across different parents
• Parallel execution for better performance
• Independent failure handling

### Inline Closures

For one-off operations, use inline closures:

<Tabs

<TabPanel id="rust" label="Rust">

```rust
#[workflow]
async fn data_processing_workflow(
    ctx: WorkflowContext,
    data_id: String,
) -> orcher::Result<ProcessedData> {
    // Inline closure for one-off operation
    let raw_data = ctx
        .execute("fetch_data", || async move {
```

**Use `ctx.execute()` (inline closures) when:**

• The logic is specific to this workflow
• You don't need to reuse it elsewhere
• It's a simple operation (< 10 lines)
• Quick one-off external API calls

**Use `ctx.execute_task()` (registered tasks) when:**

• The logic is shared across workflows
• You need centralized retry configuration
• The operation is complex
• You want better testability and separation of concerns

**Retry configuration:**

The `retry = N` shorthand caps the number of attempts. For full control, attach a
`RetryPolicy` with `max_attempts`, `initial_interval`, `max_interval`, and
`backoff_coefficient`. There is no separate strategy enum — the delay grows
exponentially per `backoff_coefficient` (use `1.0` for a fixed delay).

### Compensation (Saga Pattern)

Handle failures by undoing previous steps:

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="sdk"
>

<TabPanel id="rust" label="Rust">

```rust
#[workflow]
async fn booking_workflow(
    ctx: WorkflowContext,
    booking: BookingRequest,
) -> orcher::Result<BookingResult> {
    // Step 1: Reserve hotel
    let hotel = ctx
        .execute_task("reserve_hotel", booking.hotel_id.clone())
        .await?;
    
    // Step 2: Reserve flight
    let flight_result = ctx
        .execute_task("reserve_flight", booking.flight_id.clone())
        .await;
    
    // If flight fails, compensate by canceling hotel
    if let Err(e) = flight_result {
        ctx.execute_task("cancel_hotel", hotel.reservation_id.clone())
            .await?;
        
        return Err(e);
    }
    
    let flight = flight_result?;
    
    Ok(BookingResult { hotel, flight })
}
```

## State Management

### Workflow State

Persist state across workflow executions:

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="rust"
  queryGroup="sdk"
>

<TabPanel id="rust" label="Rust">

```rust
#[derive(Serialize, Deserialize, Default)]
struct BatchState {
    processed: usize,
    total: usize,
    failed: Vec<String>,
}

#[workflow]
async fn batch_processing_workflow(
    ctx: WorkflowContext,
    items: Vec<Item>,
) -> orcher::Result<BatchResult> {
    let mut state = BatchState::default();
    state.total = items.len();
    
    for item in items {
        match ctx.execute_task("process_item", item.clone()).await {
            Ok(_) => state.processed += 1,
            Err(_) => state.failed.push(item.id),
        }
        
        // State is automatically persisted by the context
    }
    
    Ok(BatchResult {
        processed: state.processed,
        failed: state.failed,
    })
}
```

## Best Practices

### 1. Keep Workflows Deterministic

**Don't:**

```rust
// Non-deterministic - uses system time directly
let timestamp = SystemTime::now();

// Non-deterministic - generates random values
let random_id = uuid::Uuid::new_v4();

// Non-deterministic - depends on external state
let user = database.get_user(id).await?;
```

**Do:**

```rust
// Use workflow context for deterministic time
let timestamp = ctx.time().now();

// Use workflow context for deterministic randomness
let random_id = ctx.rand().uuid();

// Wrap external calls in ctx.execute() or ctx.execute_task()
let user = ctx.execute("get_user", || async {
    database.get_user(id).await
}).await?;
```

### 2. Design for Idempotency

Ensure tasks can be safely retried:

```rust
#[task]
async fn process_payment(ctx: TaskContext, payment: PaymentRequest) -> Result<PaymentResult> {
    // Use idempotency key
    let idempotency_key = format!("payment_{}", payment.order_id);
    
    stripe::charge_with_idempotency_key(
        payment.amount,
        payment.card,
        &idempotency_key,
    ).await
}
```

### 3. Use Descriptive Step Names

```rust
// Bad
ctx.execute("step1", || async { ... }).await?;
ctx.execute("step2", || async { ... }).await?;

// Good
ctx.execute("charge_customer_card", || async { ... }).await?;
ctx.execute("reserve_inventory_items", || async { ... }).await?;
```

### 4. Handle Failures Gracefully

```rust
#[workflow]
async fn resilient_workflow(ctx: WorkflowContext, input: Input) -> orcher::Result<Output> {
    // Try primary service
    let result = ctx.execute("primary_service", || async {
        primary::process(input.clone()).await
    }).await;
    
    // Fallback to secondary service
    let result = match result {
        Ok(r) => r,
        Err(_) => {
            ctx.execute("secondary_service", || async {
                secondary::process(input.clone()).await
            }).await?
        }
    };
    
    Ok(Output::from(result))
}
```
