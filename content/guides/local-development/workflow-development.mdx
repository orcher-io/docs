This page is the loop you repeat while writing a workflow: add it to the project, run it, change it, run it again. It continues from [Getting started](/guides/local-development/getting-started), so it assumes a local engine and a project made with `orcher new`.

What a workflow may contain, and the full API, are in the SDK guides: [Python](/guides/sdk/python/workflows), [TypeScript](/guides/sdk/typescript/workflows), [Rust](/guides/sdk/rust/workflows).

## 1. Add a workflow

In the project directory:

```bash
orcher new workflow welcome
```

This writes a file with a `welcome` workflow and one task, and prints the line that registers it with the worker. Add that line next to the one already there for `workflows`:

| Language | File created | Line to add | Where |
|---|---|---|---|
| Python | `welcome.py` | `import welcome  # noqa: F401` | `worker.py` |
| TypeScript | `src/welcome.ts` | `import './welcome';` | `src/worker.ts` |
| Rust | `src/welcome.rs` | `mod welcome;` | `src/main.rs` |

A workflow the worker has not registered fails as soon as it is started, with `Unknown workflow type: welcome`.

The workflow function only decides what happens and in what order. Everything that touches the outside world is in a task. That split is what lets a worker replay the workflow after a restart: it runs the function again from the top, and each step that already finished returns its recorded result instead of running again.

## 3. Run it

Start the worker again so it loads the new code (TypeScript: `npm run build` first), then start the workflow on the project's task queue. The examples use the Python project's queue, `hello-py`:

```bash
orcher workflow start welcome --task-queue hello-py --input '"ada@example.com"' --wait
```

The worker prints `created account for ada@example.com`, then `sent welcome to ada@example.com` ten seconds later, and the command prints the result:

```
"acct-ada@example.com: welcomed ada@example.com"
```

## 4. Change it and run it again

A worker loads your code once, when it starts. After every change:

1. Stop the worker with Ctrl+C.
2. Rebuild if your language needs it (`npm run build`; `cargo run` rebuilds by itself).
3. Start the worker.
4. Start a new workflow.

Nothing is lost while the worker is down. The runs are in the engine, not in the worker. To see it, start a workflow without `--wait`, stop the worker while the workflow is in its ten-second timer, and start the worker again:

```bash
orcher workflow start welcome --task-queue hello-py --id welcome-1 --input '"ada@example.com"'
# stop the worker, start it again, then:
orcher workflow result welcome-1
```

The new worker prints `sent welcome to ada@example.com` and not `created account`: the account task already finished, so the workflow resumes after it. The timer kept running in the engine while no worker was up.

## Changes that break a run in progress

A run that started on the old code is replayed on the new code. That works as long as the new code asks for the same steps in the same order as the journal recorded. Changing what a task does inside, or the text a workflow returns, is safe. Adding, removing or reordering the steps before the point a run has reached is not.

For example, start a workflow, stop the worker during the timer, add a task call before the timer, and start the worker. The worker refuses to continue that run and logs an error. This one is from the Python worker; the task name follows your language's:

```
ERROR orcher_sdk_core::worker::drivers::workflow: Workflow "welcome" (...) is not deterministic:
step 2 of the journal (entry 5) is timer "timer-1" for 10s, which the workflow code no longer
reaches: replaying the journal, the code instead issued new work, task "task-1" of type
"send-welcome". [...] This activation is not applied and the run stays open; it is tried again
in 2s. To carry the run on, deploy the code that recorded it (or code that replays its journal
the same way), and let in-flight runs finish before deploying an incompatible change.
```

The run is not failed. It stays `RUNNING` and the worker tries it again every few seconds. On your machine there are three ways out:

- Put the old code back and restart the worker. The run continues and finishes.
- End the run and start a new one on the new code: `orcher workflow terminate welcome-1`.
- Delete everything the local engine holds: `orcher dev stop --delete-data`, then start it again.

<Admonition type="note">

This check is in the current SDKs. A Rust project generated by CLI 0.1.4 is pinned to `orcher-sdk = "0.5"`, which does not make it: the changed code runs the new step and the run never finishes. Set `orcher-sdk = "0.18"` in `Cargo.toml` before relying on this.

</Admonition>

<Admonition type="note">

The Rust SDK logs through the `tracing` crate and prints nothing until your program installs a subscriber, so a generated Rust worker shows no error here. [Debugging workflows](/guides/local-development/debugging-workflows#worker-logs) shows the lines to add.

</Admonition>

## Keep workflow code deterministic

The same rule explains what a workflow function must not do. On replay it has to make the same decisions it made the first time, so it cannot read the clock, generate random values, or call a network service or a database directly. Put those in a task, or use the workflow context's own replay-safe helpers. Each SDK guide lists them: [Python](/guides/sdk/python/workflows#time-and-randomness), [TypeScript](/guides/sdk/typescript/workflows#deterministic-helpers), [Rust](/guides/sdk/rust/workflows#determinism).
