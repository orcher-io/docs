Install the CLI, start an engine in Docker, create a project with one workflow, and run it. At the end you have a worker running your own code against an engine on your machine.

If you would rather run a finished example first, the [quickstart](/guides/getting-started/quickstart) does that without the CLI.

## Prerequisites

- [Docker](https://docs.docker.com/get-docker/), running
- For the language you pick: Python 3.11 or later, Node.js 22 or later, or stable Rust

Check that it runs:

```bash
orcher --version
```

This guide was checked with `orcher 0.1.4`. Every release also has binaries and checksums on its [release page](https://github.com/orcher-io/cli/releases).

## 2. Start the engine

```bash
orcher dev start --engine-version 0.7.5
```

The first run pulls two images, the engine and Postgres, and then prints where the engine listens:

```
Local engine
  State     ready
  Image     ghcr.io/orcher-io/orcher:0.7.5
  gRPC      http://localhost:50051
  Dashboard http://localhost:8080
  Health    http://localhost:8080/health/ready
  Database  ready
```

Workers, clients and the CLI connect to the gRPC address. The dashboard is a web page: open [http://localhost:8080](http://localhost:8080).

The engine keeps running in the background and keeps its data in a Docker volume. `orcher dev status` shows the same summary again, and `orcher dev logs` prints the engine's log.

<Admonition type="note">

Pass `--engine-version`. Without it, CLI 0.1.4 starts engine 0.6.2, which has no dashboard.

</Admonition>

<Admonition type="note">

Port taken? Pick others. The command prints the `export` line that points the CLI and your workers at the new gRPC port:

```bash
orcher dev start --engine-version 0.7.5 --port 50061 --http-port 8081
export ORCHER_SERVER=http://localhost:50061
```

</Admonition>

## 3. Create a project

`orcher new` writes a small project: a `hello` workflow that runs one `greet` task, a worker, a starter and a test.

<Tabs
  scrollable
  size="small"
  type="underlined"
  defaultActiveId="python"
  queryGroup="language"
>

<TabPanel id="python" label="Python">

```bash
orcher new python hello-py
cd hello-py
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

| File | What it is |
|---|---|
| `workflows.py` | The workflow and its task |
| `worker.py` | Runs them, polling the `hello-py` task queue |
| `start.py` | Starts `hello` and prints its result |
| `test_workflow.py` | Runs `hello` on the engine and checks the result |
| `settings.py` | The engine's address, the namespace and the API key, read from the environment |

</TabPanel>

<TabPanel id="typescript" label="TypeScript">

```bash
orcher new typescript hello-ts
cd hello-ts
npm install
npm run build
```

| File | What it is |
|---|---|
| `src/workflows.ts` | The workflow and its task |
| `src/worker.ts` | Runs them, polling the `hello-ts` task queue |
| `src/start.ts` | Starts `hello` and prints its result |
| `src/test.ts` | Runs `hello` on the engine and checks the result |
| `src/settings.ts` | The engine's address, the namespace and the API key, read from the environment |

</TabPanel>

<TabPanel id="rust" label="Rust">

```bash
orcher new rust hello-rs
cd hello-rs
```

| File | What it is |
|---|---|
| `src/workflows.rs` | The workflow and its task |
| `src/main.rs` | The worker (`worker`, polling the `hello-rs` task queue), the starter (`start`), and a test that runs `hello` on the engine |

</TabPanel>

</Tabs>

The task queue is named after the project. A worker takes work from one task queue, and a workflow is started on one, so the two names have to match.

<Admonition type="note">

CLI 0.1.4 pins the Python project to `orcher-sdk>=0.4.1,<0.5` and the Rust project to `orcher-sdk = "0.5"`. Both run as generated, but the SDK guides in these docs describe Python SDK 0.5 and Rust SDK 0.18, and the Rust 0.5 line lacks the replay check described in [Workflow development](/guides/local-development/workflow-development#changes-that-break-a-run-in-progress). Change the line to `orcher-sdk==0.5.0` in `requirements.txt`, or to `orcher-sdk = "0.18"` in `Cargo.toml`, and install again; the generated code runs unchanged on them. The TypeScript project installs the current `@orcher/sdk` 0.5 release.

</Admonition>

It prints `worker polling hello-py on http://localhost:50051` (with your project's name), followed in Python and TypeScript by the SDK's own log lines as it connects.

## 5. Start a workflow

In a second terminal, start `hello` on the project's task queue and wait for the result. The input is JSON, so a string needs its quotes:

```bash
orcher workflow start hello --task-queue hello-py --input '"world"' --wait  # Python
orcher workflow start hello --task-queue hello-ts --input '"world"' --wait  # TypeScript
orcher workflow start hello --task-queue hello-rs --input '"world"' --wait  # Rust
```

```
Started d5313967-5220-48f2-b048-bbc3984183a4 (execution e0448b9d-cf72-4da4-a09e-e32559fb7242); waiting for it to finish...
"Hello, world!"
```

The project's starter does the same from code, in the project directory:

```bash
.venv/bin/python start.py world    # Python
npm run start-workflow -- world    # TypeScript
cargo run -- start world           # Rust
```

## 6. Look at what ran

Give a workflow an id of your own and you can refer to it afterwards. These lines use the Python project's task queue; use your own:

```bash
orcher workflow start hello --task-queue hello-py --id hello-1001 --input '"Grace"'
orcher workflow result hello-1001     # wait for it, and print what it returned
orcher workflow list                  # recent workflows
orcher workflow get hello-1001        # status, times, and the result or error
orcher workflow history hello-1001    # every step the engine recorded
```

`orcher workflow history` prints the journal, the record a worker replays to resume a workflow after a restart:

```
Execution Journal (hello-1001)
----------------------------------------------------------------------------------------------------
[1] WORKFLOW_EXECUTION_STARTED 2026-11-22 20:54:10
[2] TASK_SCHEDULED 2026-11-22 20:54:10
[3] TASK_COMPLETED 2026-11-22 20:54:10
[4] STEP_COMPLETED 2026-11-22 20:54:10
[5] WORKFLOW_EXECUTION_COMPLETED 2026-11-22 20:54:10

5 journal entries
```

The dashboard at [http://localhost:8080](http://localhost:8080) shows the same runs. The lightning-bolt icon in the left rail opens **Executions**; click a row to see that run's tasks, journal and log.

## 7. Stop

Stop the worker with Ctrl+C. Then stop the engine:

```bash
orcher dev stop                  # keeps the database for the next start
orcher dev stop --delete-data    # also deletes every workflow it ran
```

## Without the CLI

The engine is a container, so Docker alone can run it. The [quickstart repository](https://github.com/orcher-io/quickstart) has a Compose file that starts Postgres and engine 0.7.5 on the same ports:

```bash
git clone https://github.com/orcher-io/quickstart.git
cd quickstart
docker compose up -d --wait     # start, and wait until the engine is ready
docker compose down -v          # stop, and delete the database
```

A project made with `orcher new` works against it unchanged, and so do the `orcher workflow` commands.
