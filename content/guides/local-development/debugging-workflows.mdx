When a workflow fails or seems stuck, the engine already holds what you need: the run's status, its error, every task attempt, and the journal of steps it recorded. This page shows where to read each of them on a local engine.

The examples use the `welcome` workflow from [Workflow development](/guides/local-development/workflow-development), whose second task fails when the input is not an email address. Start one that fails, with the Python project's task queue or your own:

```bash
orcher workflow start welcome --task-queue hello-py --id welcome-bad --input '"nobody"'
```

## Read the run

Start with the run itself:

```bash
orcher workflow get welcome-bad
```

```
Workflow Details
--------------------------------------------------
  Workflow ID:  welcome-bad
  Execution ID: 9eb31826-1c7c-4254-ac07-d05f5f863f7f
  Status:       FAILED
  Started:      2026-11-22 20:59:56 UTC
  Completed:    2026-11-22 21:00:09 UTC

Error:
  [TASK_EXECUTION_FAILED] Task 'send-welcome' failed after 3 attempts: not an email address: nobody
```

`orcher workflow get welcome-bad --full` adds the task queue and namespace, and counts of pending tasks, timers and events.

The error names the task. See each attempt:

```bash
orcher workflow tasks welcome-bad
```

```
 TASK ID | TYPE           | STATUS      | ATTEMPT | STARTED  | DURATION
---------+----------------+-------------+---------+----------+----------
 task-0  | create-account | ● Completed | 1       | just now | 52ms
 task-2  | send-welcome   | ✗ Failed    | 1       | just now | 36ms
 task-2  | send-welcome   | ✗ Failed    | 2       | just now | 26ms
 task-2  | send-welcome   | ✗ Failed    | 3       | just now | 32ms
  task-2 └─ not an email address: nobody
```

The journal shows the order things happened in, including the timer between the two tasks:

```bash
orcher workflow history welcome-bad
```

```
[1] WORKFLOW_EXECUTION_STARTED 2026-11-22 20:59:56
[2] TASK_SCHEDULED 2026-11-22 20:59:57
[3] TASK_COMPLETED 2026-11-22 20:59:57
[4] STEP_COMPLETED 2026-11-22 20:59:57
[5] TIMER_STARTED 2026-11-22 20:59:57
[6] TIMER_FIRED 2026-11-22 21:00:02
[7] TASK_SCHEDULED 2026-11-22 21:00:02
[8] TASK_FAILED 2026-11-22 21:00:02
[9] TASK_FAILED 2026-11-22 21:00:04
[10] TASK_FAILED 2026-11-22 21:00:09
[11] STEP_COMPLETED 2026-11-22 21:00:09
[12] WORKFLOW_EXECUTION_FAILED 2026-11-22 21:00:09
```

`orcher logs welcome-bad` prints the engine's own log of the run, one line per event, with each task failure's message.

To find runs without knowing their ids:

```bash
orcher workflow list -s failed       # or running, completed, cancelled
orcher workflow list --type welcome
```

## The dashboard

The engine serves a dashboard at [http://localhost:8080](http://localhost:8080). The lightning-bolt icon in the left rail opens **Executions**, a list of runs that you can filter by status. Click a run to open it: the error is at the top, and the tabs below it are **Tasks** (each task with its status and attempt count), **Timeline**, **Graph**, **Journal** and **Logs**.

The dashboard needs engine 0.7.0 or later, and it identifies a run by its execution id, the one `orcher workflow get` prints.

## A workflow that is not moving

A run that stays `RUNNING` is waiting for something. The last journal entry says what.

| What you see | What it means | What to do |
|---|---|---|
| The journal has only `WORKFLOW_EXECUTION_STARTED`. | No worker is polling the run's task queue in its namespace. The engine keeps the run until one does. | Start the worker, or compare the queue and namespace the worker printed at start with the run's: `orcher workflow get <id> --full`. |
| The journal ends in `TIMER_STARTED`, and `--full` shows `Pending Timers: 1`. | The workflow is sleeping. | Wait. The timer is kept by the engine and fires whether or not a worker is running. |
| The worker logs `is not deterministic` every few seconds. | The workflow code changed in a way that no longer matches the run's journal. | See [Changes that break a run in progress](/guides/local-development/workflow-development#changes-that-break-a-run-in-progress). |
| The run failed at once with `Unknown workflow type`. | A worker is polling the queue, but that worker has not registered the workflow. | Register it with the worker, as in [Add a workflow](/guides/local-development/workflow-development#1-add-a-workflow), and restart the worker. |

`orcher queue list` groups runs by task queue, which shows quickly whether a run went to the queue you meant.

To end a run you no longer want:

```bash
orcher workflow cancel <id>       # ask the workflow to stop
orcher workflow terminate <id>    # stop it at once
```

Both ask for confirmation; `--force` skips the question.

## Worker logs

A task that raises prints its error in the worker's terminal: a traceback in Python, a `Task failed:` line in TypeScript. That is usually the fastest place to look, because it is your own code's error. A Rust worker logs the failure once a subscriber is installed, as shown below.

The SDKs share a core that logs what the worker is doing: connecting, polling, each workflow and task it receives. The `RUST_LOG` environment variable sets how much of that it prints, in every language, because the core is written in Rust:

```bash
RUST_LOG=warn .venv/bin/python worker.py     # only warnings and errors
RUST_LOG=debug .venv/bin/python worker.py    # every poll and completion
```

Python and TypeScript workers print at `info` when `RUST_LOG` is unset. A Rust worker prints nothing from the SDK until the program installs a `tracing` subscriber. Add the dependency:

```bash
cargo add tracing-subscriber --features env-filter
```

## Engine logs

```bash
orcher dev logs                # the last 200 lines
orcher dev logs --follow       # keep printing
orcher dev logs --postgres     # the database's log instead
```

With the quickstart's Compose file, the same log is `docker compose logs -f orcher`.

The engine logs at `info`. For more, restart it at `debug`. The data is kept:

```bash
orcher dev stop
orcher server start --engine-version 0.7.2 --log-level debug
```

With Compose, set `ORCHER_LOG_LEVEL=debug` when you run `docker compose up -d --wait`.

## The REST API

Everything the CLI showed is also available as JSON on the engine's HTTP port, which is useful in scripts. The API identifies a run by its execution id, the one `orcher workflow get` prints, not by the workflow id you chose:

```bash
curl -s 'http://localhost:8080/api/v1/executions?status=FAILED&limit=10'
curl -s http://localhost:8080/api/v1/executions/<execution-id>/status
curl -s http://localhost:8080/api/v1/executions/<execution-id>/journal
curl -s http://localhost:8080/api/v1/workers
```

The journal endpoint includes what the CLI's history leaves out: the workflow's input, each task's type and each step's result. `/api/v1/workers` lists the workers the engine has seen, with the task queue each polls and the workflows and tasks each registered. With engine 0.7.2, a worker that was killed can stay listed as `idle`, so the status there does not prove a worker is running.

The CLI prints JSON too: `orcher workflow get`, `list`, `tasks` and `history` all take `-o json`.

## Start clean

When the local engine has collected more runs than you want to look through, delete them all:

```bash
orcher dev stop --delete-data
orcher dev start --engine-version 0.7.2
```

With Compose, `docker compose down -v` and then `docker compose up -d --wait`.
