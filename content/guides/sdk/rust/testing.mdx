## Testing a Workflow with Mocked Tasks

`TestWorkflowExecutor` runs a workflow function and answers each task it schedules from a `MockRegistry`. It runs the workflow, collects the tasks it scheduled, runs their mocks, and replays the workflow with the results, until the workflow returns.

<$CodeSample path="rust/sdk-testing/src/lib.rs" region="executor" />

- Pass the `#[workflow]` function itself; the macro keeps it callable.
- Mocks are keyed by the task's registered name, and every task the workflow reaches needs one.
- `WorkflowExecution::new` takes the workflow id, run id, workflow type, namespace and task queue that `ctx` reports.
- `with_max_steps(n)` limits how many times the workflow is run (1000 by default), which catches a workflow that never finishes.

## Mocking Tasks

`MockTaskBuilder::new(task_name, registry)` registers one mock:

| Method | The mock |
|--------|----------|
| `returns(value)` | Returns `value` on every call. Pass the success value, not a `Result`. |
| `returns_seq(vec![...])` | Returns the next value on each call, and fails once they run out |
| `with_fn(function)` | Computes the result from the task's input; the function takes and returns JSON bytes |
| `fails_with(message)` | Fails on every call |

## What the Test Kit Doesn't Cover

- `TestWorkflowExecutor` resolves tasks only. A workflow that waits on a timer, an event or a child workflow stops with an error at that point.
- A mocked task never fails *into* the workflow, so failure handling (`WorkflowError::TaskFailed`, compensation) isn't exercised.
- Task code never runs, and nothing is persisted or replayed from a real journal.
- `TestEnv` records whether each run completed, but not the tasks or state of a run. Its `advance_time` moves a `MockClock` for your own code; it doesn't fire `ctx.sleep` timers.

For the rest, run the workflow against a server: start the engine locally, run a worker in the test process or beside it, and drive it with a `Client`.
