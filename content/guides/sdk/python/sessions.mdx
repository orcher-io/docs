Tasks normally run on whichever worker polls their queue first. A **session** sends a series of tasks to one worker, so they can share what that worker holds locally:

- files a task downloaded to the worker's disk, for the next task to transform;
- a model loaded into memory, for several inference tasks to use; or
- open connections or other in-process state.

## When no worker has room

Each worker hosts up to 10 sessions at a time. A worker with no free slot doesn't wait for one: the session's creation fails, the engine retries it like any task (possibly on another worker), and once those attempts are used up `create_session()` raises `TaskError`. Handle that by waiting and trying again. The same loop starts over in a new session when a task in the session fails, which is also how to recover from losing the session's worker (see [Limitations](#limitations)):

## SessionOptions

| Field | Default | Description |
|---|---|---|
| `creation_timeout` | `timedelta(seconds=30)` | How long creating the session may take; it is the timeout of the creation step |
| `execution_timeout` | `timedelta(seconds=600)` | How long the session may stay open; past it the worker closes the session and frees its slot |
| `max_concurrent_tasks` | `1` | Sent to the worker, but not enforced |
| `heartbeat_interval` | `timedelta(seconds=5)` | Sent to the worker, but not used |

Because `execution_timeout` is not enforced, a session that is never completed holds its slot until the worker restarts.

## How it works

Sessions are built from task queues; the engine has no separate session concept.

1. `create_session()` schedules an internal task, `__orcher_create_session`, on the workflow's queue.
2. The worker that picks it up takes a session slot and starts polling a queue of its own, named `<queue>__session__<id>`, where the id is generated by that worker process.
3. The task's result, the queue name, is journaled, so a replay reuses the same session.
4. `session.execute_task()` schedules each task on that queue, which only that worker polls.
5. `session.complete()` schedules `__orcher_complete_session` on the session queue; the worker stops polling it and frees the slot.

---

## Limitations

- **A session ends with its worker.** If the worker stops while one of the session's tasks is running, that task times out (its heartbeat timeout, a minute by default) and the engine fails it and every other task on the session's queue as lost; the workflow gets a `TaskError` and can open a new session. A task only waiting on the queue is caught by its own `queue_timeout`, which by default is none, so give session tasks a `queue_timeout`, catch the `TaskError`, and start over in a new session, as the example above does.
- **Everything runs on one machine.** For work that can run anywhere, use ordinary tasks, which spread across workers.
- **Capacity is fixed.** Ten sessions per worker, not configurable from Python; run more workers for more sessions.
