## Workflow Execution

### Execute Workflow

Start a new workflow execution.

```bash
POST /api/v1/workflows/execute
Authorization: Bearer <token>
Content-Type: application/json

{
  "workflow_type": "order_processing",
  "workflow_id": "order-12345",
  "task_queue": "orders",
  "input": {
    "order_id": "12345",
    "customer_id": "cust_789",
    "amount": 99.99
  },
  "execution_timeout": 3600,
  "retry_policy": {
    "max_attempts": 3,
    "initial_interval": 1,
    "backoff_coefficient": 2.0,
    "maximum_interval": 60
  }
}
```

**Response:**

```json
{
  "execution_id": "exec_abc123",
  "workflow_id": "order-12345",
  "run_id": "run_xyz789",
  "status": "running",
  "created_at": "2024-01-07T12:00:00Z"
}
```

### Get Execution Status

```bash
GET /api/v1/executions/:execution_id/status
Authorization: Bearer <token>
```

**Response:**

```json
{
  "execution_id": "exec_abc123",
  "workflow_id": "order-12345",
  "run_id": "run_xyz789",
  "status": "completed",
  "started_at": "2024-01-07T12:00:00Z",
  "completed_at": "2024-01-07T12:05:30Z",
  "duration_ms": 330000,
  "progress": {
    "current_step": 5,
    "total_steps": 5,
    "percentage": 100
  }
}
```

**Status Values:**
- `pending` - Execution queued
- `running` - Currently executing
- `completed` - Finished successfully
- `failed` - Execution failed
- `canceled` - Canceled by user
- `timed_out` - Exceeded timeout

### Cancel Execution

```bash
POST /api/v1/executions/:execution_id/cancel
Authorization: Bearer <token>
Content-Type: application/json

{
  "reason": "Customer requested cancellation"
}
```

**Response:**

```json
{
  "execution_id": "exec_abc123",
  "status": "canceled",
  "canceled_at": "2024-01-07T12:03:00Z"
}
```

### Reset Execution

Rewind a workflow to a specific journal point and re-execute from there. The original execution is marked as "reset" (terminal) and a new execution is created with the journal history preserved up to the target event.

This is useful for recovering from bad deployments, debugging production failures, or retrying from a known-good checkpoint without re-running from scratch.

```bash
POST /api/v1/executions/:execution_id/reset
Authorization: Bearer <token>
Content-Type: application/json

{
  "target_event_id": 5,
  "reason": "Bad deployment caused task failures after step 5"
}
```

**Request Body:**

- `target_event_id` (required) - Journal event ID to reset to. All events up to and including this ID are preserved; events after it are discarded.
- `reason` (optional) - Human-readable reason recorded in the journal.

**Response:**

```json
{
  "new_execution_id": "exec_def789",
  "old_execution_id": "exec_abc123"
}
```

The new execution replays the preserved journal (completed steps are skipped via cache), then continues executing from the reset point making fresh decisions.

### List Executions

```bash
GET /api/v1/executions?workflow_type=order_processing&status=running&limit=50&offset=0
Authorization: Bearer <token>
```

**Query Parameters:**
- `workflow_type` - Filter by workflow type
- `status` - Filter by status
- `workflow_id` - Filter by workflow ID
- `from` - Start date (ISO 8601)
- `to` - End date (ISO 8601)
- `limit` - Results per page (default: 50, max: 100)
- `offset` - Pagination offset

**Response:**

```json
{
  "executions": [
    {
      "execution_id": "exec_abc123",
      "workflow_id": "order-12345",
      "workflow_type": "order_processing",
      "status": "running",
      "started_at": "2024-01-07T12:00:00Z"
    }
  ],
  "total": 150,
  "limit": 50,
  "offset": 0,
  "has_more": true
}
```

### Get Execution Logs

```bash
GET /api/v1/executions/:execution_id/logs?level=info&limit=100
Authorization: Bearer <token>
```

**Query Parameters:**
- `level` - Filter by log level (debug, info, warn, error)
- `limit` - Number of logs to return
- `from` - Start timestamp
- `to` - End timestamp

**Response:**

```json
{
  "execution_id": "exec_abc123",
  "logs": [
    {
      "timestamp": "2024-01-07T12:00:01Z",
      "level": "info",
      "message": "Workflow started",
      "context": {
        "step": "initialization"
      }
    },
    {
      "timestamp": "2024-01-07T12:00:05Z",
      "level": "info",
      "message": "Task completed: charge_payment",
      "context": {
        "task_id": "task_123",
        "duration_ms": 1500
      }
    }
  ],
  "total": 45
}
```

### Stream Execution Logs (SSE)

Stream real-time logs using Server-Sent Events.

```bash
GET /api/v1/executions/:execution_id/logs/stream
Authorization: Bearer <token>
Accept: text/event-stream
```

**Response (SSE Stream):**

```text
event: log
data: {"timestamp":"2024-01-07T12:00:01Z","level":"info","message":"Workflow started"}

event: log
data: {"timestamp":"2024-01-07T12:00:05Z","level":"info","message":"Task completed"}

event: complete
data: {"execution_id":"exec_abc123","status":"completed"}
```
